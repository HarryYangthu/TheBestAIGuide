# 运维 Agent：先形成可审查诊断，再决定是否执行变更

> 状态：draft · 更新：2026-09-06

教学输入：最近错误率 8%，并且上升发生在发布后。规则输出 `request_rollback_review`，附上错误率和发布时间两类证据。这个输出只表示“值得审查回滚”，不是已经证明发布是根因，更不是已执行生产回滚。

相关性来自时间共现：发布可能导致故障，也可能恰好撞上流量变化或下游事故。进一步诊断应查看版本分组错误、未变更实例、请求类型与依赖指标。用 Agent 帮忙收集和组织证据，比让它看到一个告警就自动改生产更容易验收。

| 阶段 | 读什么 | 输出什么 |
|---|---|---|
| 定位影响 | 错误率、请求量、用户影响 | 问题窗口与范围 |
| 形成假设 | 发布、配置、依赖变化 | 可被证伪的原因候选 |
| 比较证据 | 新旧实例、正常异常请求 | 支持与冲突证据 |
| 提出变更 | 回滚对象、影响、验证与恢复步骤 | 待批准计划 |
| 验证效果 | 同口径窗口与业务 SLI | 恢复/未恢复结论 |

[application_cases.py](../../../05-code/application_cases.py)只实现第一条教学规则，错误率较低或缺少发布时间关系时返回 `collect_more_evidence`。它没有访问日志平台、没有调用生产 API，也没有测量真实系统指标。

若后续允许执行，必须把批准绑定具体版本/服务/参数，并限制动作速率。回滚后同口径错误率下降是支持证据，但依然要排除流量变化；不能仅凭“命令返回 0”宣布恢复。SLO 与错误预算方法见[Google SRE](https://sre.google/workbook/implementing-slos/)，对应本库[生产指标篇](../../../../14-production-engineering/01-concepts/02-slos-reliability-and-cost.md)。
