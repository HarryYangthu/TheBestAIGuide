# 存储与多租户：正确答案也可能泄露给错误的人

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

假设两个团队都问“预算还有多少”，查询向量相似并不能决定它们可以读取同一条答案。多租户系统首先要确定数据属于谁、谁可访问，再做检索与缓存。

## 不同数据为什么用不同存储

| 对象 | 适合保存的内容 | 需要的性质 |
|---|---|---|
| Run 状态数据库 | 任务归属、状态、版本、动作记录 | 条件更新、事务、索引 |
| 事件日志 | 顺序事件、调用结果引用 | 可追加、可重放、保留策略 |
| 对象存储 | 文档、图片、视频和生成产物 | 完整性摘要、版本、访问控制 |
| 检索索引 | 分块、向量、来源与权限标签 | 过滤、更新、删除一致性 |
| 缓存 | 可重新生成的结果 | TTL、隔离键、失效条件 |

原文删除后，只删对象存储而留下向量和摘要，仍可能泄露内容。因此每个派生对象应记录来源 ID，删除按依赖传播并留审计记录。审计记录本身也应最小化，避免为“证明已删除”永久保存完整敏感原文。

## 权限过滤要发生在哪里

身份由认证层得到，不接受模型或请求正文自报 tenant_id。访问 Run、对象下载、事件补发、向量召回和缓存命中都要做授权；只在页面入口检查一次不够。检索前过滤可以避免把其他租户候选交给模型；检索后仍应核对最终引用。

PostgreSQL 行级安全策略可以作为数据库层防线，但表所有者、超级用户和 BYPASSRLS 角色有特殊规则。应用使用普通受限角色；需要时启用 FORCE ROW LEVEL SECURITY，并针对实际部署角色做测试。不能用超级用户跑通查询就宣布隔离有效。

```sql
-- 教学配置片段；先在隔离数据库验证角色和连接池策略。
ALTER TABLE runs ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_runs ON runs
  USING (tenant_id = current_setting('app.tenant_id', true));
```

`app.tenant_id` 必须由可信服务端在事务内绑定，并在连接复用时正确清理。它不应由可执行任意 SQL 的客户端设置。该片段不是已运行的数据库工程。

## 缓存键也是权限边界

至少考虑租户、访问主体/权限版本、模型配置、输入摘要、检索文档版本与工具版本。同租户也可能存在不同权限，不要仅以 tenant_id 作为充分条件。语义缓存对只读问答可能有用，对付款、写库等动作不能用相似问题复用结果。

```python
key = (tenant_id, acl_version, model_version, document_version, prompt_hash)
```

这是键结构示意，需要根据业务把权限主体纳入，且命中后仍检查当前授权。[企业案例](../03-cases/domain-agents/enterprise/README.md)提供可运行的跨租户反例；正式规范见[PostgreSQL 行安全文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)，所有系统设计还需按[来源索引](../references.md)中的范围理解。
