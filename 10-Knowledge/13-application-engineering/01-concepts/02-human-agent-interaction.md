# 人机交互：让用户知道已做什么、将做什么和依据是什么

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

一个长任务界面只显示“正在思考”，用户既不知道它是否卡住，也不知道能否介入。好的交互应显示可核验的执行状态，并提供改计划、取消、查看证据和批准具体动作的入口。

## 哪些信息值得展示

用户要看的是当前目标、已完成步骤、遇到的障碍、必要的待确认事项和结果依据。可以展示简短的计划与决策理由，不必暴露模型内部推理文本。工具调用显示人能理解的动作，如“读取合同第 3 页”，而不是原始 HTTP payload；详细调试日志留在开发者视图并脱敏。

| 时刻 | 用户应该看到 | 后端需要保存 |
|---|---|---|
| 开始 | 目标、范围、预计步骤 | 原始请求与版本化计划 |
| 执行中 | 已完成动作和当前步骤 | 结构化事件 |
| 缺信息 | 哪个字段缺失，如何影响结果 | 等待原因与可恢复状态 |
| 有副作用 | 将提交的对象、参数和影响 | 与参数绑定的批准记录 |
| 完成 | 产物、证据、未解决事项 | 可再次打开的产物版本 |

## 批准必须绑定一个具体动作

用户批准“把金额 100 元填入测试单”，之后模型把金额改成 1000 元，旧批准不应继续有效。为待批准动作计算规范化参数摘要，批准记录关联用户、动作 ID、摘要、有效期和作用域。执行时重新核对，不接受模型自己写的 `approved=true`。

```python
import hashlib, json

def action_digest(action):
    canonical = json.dumps(action, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()

assert action_digest({"amount":100}) != action_digest({"amount":1000})
```

这个摘要只负责检测参数变化，不负责身份认证，也不是数字签名。服务端仍需验证批准者身份与权限。[浏览器工程](../05-code/browser-agent-typescript/README.md)用独立的 grant 集合作为测试权限输入，页面内容和模型动作都不能自行授予权限。

## 人改计划后怎么办

计划应有版本。用户编辑第 2 步时，已经完成的第 1 步作为事实保留，依赖第 2 步的待执行项重新计算。正在进行的动作需要明确取消或等待完成；不能一边运行旧计划，一边在 UI 上显示新计划。恢复后显示上次确认的事实和未决动作，避免让用户重新解释全部背景。

完成状态也需要验收条件。按钮点击完成，只能展示“已点击”；页面出现记录且独立查询确认后，才能展示“已创建记录”。本库[本地浏览器案例](../03-cases/browser-agents/README.md)同时检查 DOM 与截图，截图便于人审，DOM 断言用于自动验收。相关机制参考[Playwright 可操作性](https://playwright.dev/docs/actionability)与[SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)，上述产品交互是本库工程设计。
