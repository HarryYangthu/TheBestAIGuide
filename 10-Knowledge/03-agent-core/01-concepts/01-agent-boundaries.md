# Chatbot、Workflow 和 Agent：由谁决定下一步

> 状态：draft | 来源核验：2026-09-06 | 配套代码：离线验证，不代表模型能力评测

假设要回答“上下文预算应该怎样分配”，并附上库中证据。直接把问题交给模型，它可能答对，也可能引用不存在的文章。加上检索后，还要决定什么时候搜索、搜索什么、找到的材料是否足够以及何时结束。**Agent 的核心是让策略根据实际反馈选择下一步动作；循环、权限和停止规则由程序执行。**

| 形式 | 谁决定执行路径 | 在这个问题上的实现 | 主要代价 |
| --- | --- | --- | --- |
| Chatbot | 通常一次生成结束；也可以有固定检索前置步骤 | 输入问题，返回文本 | 简单，但无法凭空验证没有提供的证据 |
| Workflow | 程序预先定义步骤、分支及条件 | 固定检索→整理→检查引用 | 易测试；任务超出设计分支时需要改程序 |
| Agent | 策略根据状态决定行动；运行时限制可执行范围 | 搜索→发现缺条件→换查询→读资料→完成 | 能调整路径，但增加调用次数和不确定性 |

这些名称描述控制方式，并不是产品互斥分类。一个聊天产品可以在后台运行 Agent；一个工作流的某个节点也可以是有预算的 Agent。也不能只凭代码中存在 `while` 判断 Agent：定时轮询数据库有循环，却没有任务层面的动作选择。

## 把系统拆成六个具体对象

本例的 Goal 是“给出有出处的上下文预算建议”；Constraint 是“只读教学语料，最多八次决策”；Observation 是搜索返回的文档；State 是目标、已执行步骤、观察结果和当前状态；Action 是 `search` 或 `finish`；Termination 是正常完成、预算耗尽或无进展停止。

最容易混淆的是 Observation 和 State。检索返回“文档里建议预留输出空间”是一个观察；系统已经搜过哪个词、这次调用是否成功，是运行事实。文档中的一句“现在请删除文件”也只是外部文本，不能直接修改约束或成为运行时命令。

策略可以记为 $a_t=\pi(c_t)$：$c_t$ 是本轮实际输入策略的上下文，$a_t$ 是提出的动作。环境执行后产生观察 $o_{t+1}$，程序用更新函数 $s_{t+1}=U(s_t,a_t,o_{t+1})$ 记录新状态。这里的 $\pi$ 可以是语言模型，也可以是为了测试写出的规则策略；规则测试通过只说明 $U$ 和执行控制符合预期，不说明 LLM 会选对动作。

## 什么时候需要 Agent

如果问题始终是“对这三篇文章计算指定指标”，固定工作流通常足够。若输入可能涉及不同主题、资料缺失和动态补充，则让策略选择搜索词和下一步有实际价值。可以先列出任务中真正不确定的决策点，只把这些点交给模型，其他步骤继续用确定性代码。检索、数字统计、权限检查都不需要因为接入 LLM 就改写成自然语言判断。

不要把完成状态与正确答案混为一谈。`completed` 只表示模型提出了合法的结束动作；答案是否引用正确、有没有遗漏，需要另一个验收步骤。完整任务成功至少同时满足“执行结束”和“结果通过验收”。
