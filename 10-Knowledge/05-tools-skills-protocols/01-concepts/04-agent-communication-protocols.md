# Agent之间传什么：任务、状态和产物

> 状态：draft | 来源核验：2026-09-06 | A2A规范页面按核验日快照阅读；本库未实现完整A2A端点

主Agent把“比较上下文压缩方法”交给研究Agent。对方可能要读多篇文章，中途需要补充限定范围，最后交付一张比较表。这比调用一个立即返回的`search`函数多了任务身份、持续状态、补充输入和产物版本的问题。

Agent通信协议要表达的核心是：委托什么目标，对方现在进行到哪一步，产物是什么，以及双方怎样恢复联系。A2A是面向独立Agent系统的互操作协议之一。它不要求双方使用相同内部框架，也不意味着接收方必须暴露自己的所有提示词、工具或私有状态。

| 对象 | 本例中的内容 | 为什么要分开 |
| --- | --- | --- |
| 能力描述 | 能做文献比较、接受哪些输入与认证方式 | 先确认对方适合任务，而非先发送全部资料 |
| Task | “比较压缩方法”及任务ID | 区分同时存在的多项委托 |
| Status | 工作中、需要输入、完成或失败 | 收到消息不代表任务已完成 |
| Message | 补充“只比较文本上下文” | 一次交流不一定是最终产物 |
| Artifact | 比较表、来源清单、版本标识 | 可被引用、保存、更新和独立验收 |

## 交接契约写到什么程度

交接输入应包含目标、约束、可用资料范围、预算和验收条件。例如“每种方法至少说明失效条件，并附来源ID”；这比“请深入研究”更容易验证。接收方返回产物时，同时说明完成项、缺失项和使用证据。主Agent负责验收，不因为对方返回`completed`就直接宣布用户任务完成。

本库内部交换示例可以使用如下对象，**它不是A2A协议的JSON线格式**：

```json
{
  "task_id": "compare-context-1",
  "input": {"topic": "上下文压缩", "scope": "local-documents"},
  "expected": {"required_sections": ["机制", "代价", "失效条件"]},
  "metadata": {"contract_version": 1, "synthetic": true}
}
```

真实接入A2A时，必须写适配器映射任务对象、状态枚举、产物和错误；不要把库内字典直接发出去假装兼容。官方规范在持续演进，具体字段、流式更新与版本协商必须依据选定规范，而不是混合复制不同版本教程。

## 三种容易忽略的失败

重复投递可能让接收方执行两次：应有业务任务ID和明确去重策略。消息丢失可能让主Agent一直等待：需要按任务ID查询状态或重新订阅。产物更新可能使主Agent引用旧版：应把版本/内容哈希与来源一起保存，而不是只记文件名。协议提供表达方式，去重、存储和重连策略仍需要两端实现。

跨Agent传递的资料应尽量小：目标、必要证据、资源指针，而非整个主Agent上下文。模型摘要不能改变用户授权范围，接收方还需检查资源访问权限。
