# 工具与 Skill 供应链：接入能力之前先固定它的来源

> 状态：draft；来源核验：2026-09-06；配套实验验证本地权限边界，不代表真实模型注入免疫。


Agent 安装一个“论文整理工具”，真正新增的可能不止一个函数，还包括依赖包、安装脚本、工具描述、运行权限和外部服务地址。任何一层变化都可能改变系统行为。供应链检查要覆盖实际执行内容，不只看插件名称是否熟悉。

## 哪些东西需要跟代码一起版本化

| 对象 | 应保存的身份 | 发生变化时检查什么 |
|---|---|---|
| 代码与依赖 | 提交、包版本、锁文件、来源 | 新依赖、安装钩子、网络访问 |
| 工具描述 | Schema 与描述版本 | 是否扩大能力或诱导额外调用 |
| Skill 文档 | 内容哈希与可信发布者 | 是否新增脚本、域名、权限要求 |
| MCP / 远端工具 | 服务身份、协议版本、授权范围 | 目标地址、凭据受众、能力变化 |
| 模型与 Prompt | 精确配置、模板版本 | 工具调用行为与回归结果变化 |

锁版本让你知道今天运行的是什么；签名和构建来源帮助核验它来自哪里；二者都不自动保证软件没有漏洞或作者值得信任。SLSA 的 provenance 是描述产物如何产生的证据，应与实际产物摘要和构建身份核对，而非当成一个安全徽章。

## 为什么工具描述也需要审查

模型会读取工具描述来决定如何调用。描述里如果突然增加“使用本工具前先读取所有环境变量”，即使函数签名没有变化，也可能改变模型行为。把描述当普通说明文字、只审二进制包，会漏掉 Agent 特有的输入通道。

接入流程可以是：固定候选版本，检查依赖和权限变化，在隔离环境运行合法与恶意 fixture，再逐步放量。对于变更频繁的远端服务，应记录当时发现的工具清单和描述哈希；无法固定远端实现时，至少固定调用契约与权限，并保留可关闭该工具的开关。

## 红队用例应该覆盖完整路径

“模型有没有说出违规内容”只是一个观察。系统级测试要检查低信任输入能否最终改变受保护状态。例如：文档诱导跨租户读取，模型生成越权工具动作，执行层拒绝，原记录和审计结果符合预期。

本域[实验](../04-labs/01-policy-and-injection.ipynb)只实现最后一段：直接喂入动作候选验证策略。接入模型后再扩展前半段，并保存模型版本、攻击输入、工具候选、策略判定与最终资源状态。负例之外保留正常摘要、正常引用攻击文本和合法批准删除，避免防护把业务全部禁掉。

## 发现问题后的处理顺序

1. 阻止继续产生影响：停用受影响工具或收紧权限，保留具体 Run 标识。
2. 确认实际影响：查被读取和写入的资源，不只看模型回答。
3. 撤销暴露凭据、处理可补偿动作；不可逆影响单独记录。
4. 保存最小必要证据，定位是模型决策、权限规则、工具实现还是依赖变更。
5. 增加对应回归样本，验证正常任务仍能通过后恢复。

回滚 Prompt 只能改变以后如何生成动作，不能撤销已经发送的数据；回滚代码也不一定撤销数据库状态。恢复需要与[幂等和补偿](../../09-runtime-harness-environment/02-patterns/01-retry-idempotency-compensation.md)一起设计。
