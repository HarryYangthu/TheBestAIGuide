# 计算基础：模型为什么装得下却跑不快

> 状态：draft · 来源核验：2026-09-06 · 本文容量例子为公式估算，不是硬件实测。

模型能否运行，首先受容量限制；运行多快，还取决于数据搬运、计算量和并行调度。仅凭参数量或显卡峰值 FLOPS，无法推导真实服务速度。应该先估算资源，再用目标形状和负载测量。

## 1. CPU、GPU、TPU 的差别如何影响程序

CPU 擅长复杂控制流、较低延迟的少量计算与通用系统任务；GPU 用大量并行执行单元处理规则的大张量计算；TPU 等专用加速器围绕矩阵计算和配套编译/内存体系设计。具体吞吐受形状、dtype、内核和数据布局影响，不能把设备类别当作性能结论。

一个大矩阵乘法通常能让加速器忙起来，成千上万次小 Python 循环或小 kernel 则可能主要花在调度上。把数据放到 GPU 后又每一步复制回 CPU，会让通信掩盖计算收益。批量化和融合算子经常比“换更大卡”更有用，但需要实测延迟代价。

## 2. 显存要分成几笔账

推理显存约为权重＋KV Cache＋激活与临时工作区＋运行时开销；训练还要保存梯度、优化器状态以及反向需要的中间激活。

如果有 $P$ 个参数，每个权重 $b_w$ 字节，权重占用是 $Pb_w$。7B 参数采用两字节存储约为 14 GB（十进制），约 13.0 GiB（二进制）。这只是权重，并不表示一张 14 GB 卡可稳定服务它。某些混合精度 Adam 方案还包含 FP32 主权重、梯度和两个状态，静态每参数内存可能达到十几字节，具体取决于实现与分片策略。

标准注意力的 KV 容量估算为：

$$M_{KV}=2BLTH_{KV}d_hb_{KV}.$$

$B$ 是并发序列数，$L$ 是层数，$T$ 是缓存长度，$H_{KV}$ 是 K/V 头数，$d_h$ 是每头维度，$b_{KV}$ 是每元素字节数，前面的2对应K和V。以 $B=1,L=32,T=4096,H_{KV}=8,d_h=128,b_{KV}=2$ 为例，结果为 536,870,912 字节，即 0.5 GiB。并发翻四倍，其他条件不变，KV 也翻四倍。滑动窗口、缓存量化和其他架构要另算。

## 3. 算力瓶颈与带宽瓶颈

算术强度 $I$ 定义为运算量除以从某级内存搬运的字节数，单位 FLOP/byte。Roofline 思路给出粗略上界：

$$\mathrm{throughput}\le\min(F_{peak},B_{mem}I).$$

$F_{peak}$ 是该精度下计算峰值，$B_{mem}$ 是带宽。设某次运算需要 100 GFLOP、搬运 10 GB，算术强度为 10 FLOP/byte。即便计算峰值很高，若每秒只能搬 1 TB，理想带宽上界也是约 10 TFLOP/s，未计其他开销。不要把理论上界当作实际测量。

大批次矩阵乘法可以复用权重，往往更容易受算力限制；小批次自回归 decode 每一步只生成少量 token，却要读取大量权重和缓存，常容易受带宽限制。Prefill 一次处理长输入，负载结构又不同。增加 batch 有时提高吞吐，却增加排队时间和显存，因此要同时看 TTFT、单 token 延迟和每秒完成请求数。

## 4. 数值精度改变的是范围、分辨率和误差

FP32、FP16、BF16 都是浮点格式，但指数和有效位分配不同。BF16 的指数范围接近 FP32，有效位较少；FP16 有更窄范围，训练时可能需要 loss scaling 避免梯度下溢。不能因为都占两字节就认为数值行为相同。

整数对称量化常写为 $q=\mathrm{clip}(\mathrm{round}(w/s),-q_{max},q_{max})$，重构 $\hat w=sq$。减小位宽缩小存储，却引入舍入与截断误差；少数大离群值可能撑大尺度 $s$，让小权重分辨不清。分通道/分组尺度可改善误差，但增加元数据和内核复杂度。

```python
qmax = 127
scale = max(abs(weights).max() / qmax, 1e-12)
q = np.clip(np.rint(weights / scale), -qmax, qmax).astype(np.int8)
restored = q.astype(float) * scale
```

量化减少字节数不必然减少延迟：内核是否使用低精度计算、是否频繁反量化、矩阵形状是否对齐都很关键。剪枝同理，普通稀疏零元素仍用密集矩阵内核计算时未必提速。

## 5. 可复现实测的最小记录

至少记录设备与驱动、库版本、精度、模型版本、输入/输出长度、batch、预热、测量次数和统计分位数。异步设备执行要同步后计时；否则计到的是任务入队时间。固定种子无法消除不同硬件内核的数值差异；要明确允许的误差容限。

排查顺序是：先确认显存组成，再测实际时延，判断主要在数据加载、CPU、GPU计算、内存带宽还是通信；最后修改与瓶颈对应的部分。不要在没有 profiler 证据时把慢归咎于 Python 或显卡。
