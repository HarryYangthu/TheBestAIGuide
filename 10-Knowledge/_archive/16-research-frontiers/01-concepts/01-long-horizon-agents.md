# 长程 Agent：为什么每一步都不错，整项任务仍会失败

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

> 研究快照：2026-09-06。本文选取已核验的代表工作解释机制，不声称覆盖当日全部最新研究，也不报告未经复现的系统成绩。

单步成功率很高，并不代表几十步后能完成任务。如果每一步都必须成功，且为方便分析假设各步独立、成功率相同为 $p$，那么 $T$ 步全部成功的概率是 $p^T$。$p=.98,T=50$ 时约为 .364。真实错误有关联，恢复也可能弥补错误，所以这个数不是对真实 Agent 的预测；它说明长任务不能仅优化单步答案质量。

## 长程任务到底多了哪些问题

| 问题 | 机制 | 可检验的改动 |
|---|---|---|
| 目标漂移 | 新观察挤占最初目标和约束 | 独立目标对象与完成条件 |
| 重复劳动 | 已完成步骤未成为持久事实 | 动作账本、状态版本、可查询产物 |
| 摘要丢信息 | 压缩把限制与证据来源删掉 | 必保字段、原始轨迹回链、压缩回归 |
| 计划失效 | 环境改变而旧计划仍执行 | 观察后检查前置条件、有限重规划 |
| 不确定副作用 | 动作成功但响应丢失 | 幂等 ID 和结果查询 |
| 预算耗尽 | 长分支缺乏中止条件 | 每层预算和无进展检测 |

外置状态减少依赖上下文记忆，但状态也可能写错。因此“主 Agent 说完成”与“验收器确认完成”应有不同字段。只存自然语言日志很难判定一个动作是否已经产生副作用。

## 论文里哪些机制可以借鉴

[Voyager v1（2023-05-25）](https://arxiv.org/abs/2305.16291v1)在 Minecraft 中组合自动课程、可执行技能库和环境反馈迭代。可迁移的思想是把已验证行为作为可检索代码保存，而不是每次重写。Minecraft 任务与企业流程的环境、权限和评价不同，不能直接据此断言企业任务也会获得同样收益。

[SWE-agent v1](https://arxiv.org/abs/2405.15793v1)强调 Agent 与计算机之间的接口设计。可学习之处是限制观察和编辑操作的形式，减少无效工具交互；这支持研究接口层，不代表只改接口就足够解决所有长程失败。

## 怎样做一个有说服力的实验

固定模型、任务、工具权限和总预算，比较“完整历史”“滑动窗口”“结构状态 + 原文检索”三种策略。任务要跨越多个阶段，并埋入早期约束；中途注入工具错误和进程中断。除最终成功外，记录重复动作、约束违背、恢复时间与总成本。不能让改进版获得更多工具调用次数后只比较成功率。

```python
from math import prod
illustrative_probability = prod([.98] * 50)
assert .36 < illustrative_probability < .37
```
