# 公开系统分析：把 SLO 从监控数字变成决策依据

> 状态：draft · 更新：2026-09-06

来源为 Google《SRE Workbook》的 [SLO Engineering Case Studies](https://sre.google/workbook/slo-engineering-case-studies/)，由 Evernote 与 The Home Depot 的实践者介绍采用 SLO 和错误预算的过程。这里分析的是公开可靠性方法，不声称这些公司已经采用本文设计的 Agent 系统，也不引用当前业务规模。

这个案例的可迁移点是：可靠性目标需要与用户体验和团队决策相连，不能只由运维选一个漂亮的可用率数字。产品和研发需要明确什么失败最伤害用户，以及预算用尽后如何调整发布与可靠性工作。

下面把这种方法应用到一个**原创教学 Agent 服务**，数字都是设计假设：月内 10000 个合格任务，目标 99% 在规定时限内通过验收，允许 100 次失败。服务目前失败 70 次，剩余 30 次预算。若 API 仍返回 200，但其中任务未通过验收，这些任务必须进入业务失败统计。

| 设计问题 | 教学服务的明确选择 | 为什么这样定义 |
|---|---|---|
| 用户关心什么 | 指定时间内得到有效产物 | 接口连通不代表任务完成 |
| 什么进入分母 | 范围内合法任务，含服务超时 | 避免剔除系统造成的失败 |
| 何时告警 | 多窗口预算消耗异常 | 减少短时少量样本误导 |
| 是否发布 | 结合剩余预算和回归结果 | 发布速度与可靠性共同决策 |

[production_checks.py](../../05-code/production_checks.py)实际计算剩余预算和单位成功任务成本，未对生产流量做压测。要落地，还需采集真实验收事件、锁定统计窗口、校准分母和建立值班响应。相关概念见[SLO 篇](../../01-concepts/02-slos-reliability-and-cost.md)。
