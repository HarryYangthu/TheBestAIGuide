# 发布与恢复：回滚代码为什么不能撤销已经发生的动作

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

Agent 新版把同一张工单创建两次，回滚容器只能阻止新错误，不能删除已经产生的重复工单。发布设计要同时处理软件版本、任务状态和外部副作用。

## 什么需要一起版本化

一次运行记录模型标识、Prompt、工具 Schema、Runtime、检索索引、记忆策略和验证器版本。某个参数变动也可能改变行为，单独记录代码 commit 不够。依赖外部模型别名时记录请求时间和实际响应标识；如果供应商不暴露精确版本，就如实声明复现限制。

已开始的任务可以固定旧版本执行完，或显式迁移状态后由新版接手。不能在一次工具调用前后悄悄更换状态字段含义。数据库迁移先新增兼容字段、双读/转换、确认旧 Worker 退出，再清理旧字段，这比先删字段再期待回滚可靠。

## 发布门禁的最小组合

| 门禁 | 关注内容 | 为什么不能被其他门禁替代 |
|---|---|---|
| 契约测试 | 输入输出、错误与权限 | 成功率高也可能偶发越权 |
| 固定任务回归 | 同环境、同预算的新旧结果 | 构建成功不证明任务可完成 |
| 故障注入 | 超时、崩溃、重复消息 | 正常路径不会覆盖不确定提交 |
| 小流量灰度 | 实际分布下的成功与成本 | 离线集未覆盖全部真实输入 |
| 恢复演练 | 旧版可启动、状态可读、未决动作可查 | “有回滚按钮”不等于可恢复 |

灰度尽量按用户或租户稳定分组，避免同一任务在两个版本之间来回切换。影子执行涉及写动作时必须使用无副作用模式或隔离环境，不能对真实用户操作两遍。

## 崩溃窗口要具体到哪一步

“写数据库 → 记录完成”之间崩溃，恢复端不知道写入是否成功。解决通常依赖下游幂等键或可查询的业务 ID；单纯在内存里记一个 `done` 无效。本库[故障复盘](../03-cases/failure-postmortems/README.md)用同一动作 ID 对比重复执行与幂等写入。[浏览器案例](../../13-application-engineering/03-cases/browser-agents/README.md)实际在提交后、checkpoint 前注入中断，再读取页面记录恢复。

```python
if operation_id in external_system_records:
    result = external_system_records[operation_id]
else:
    result = external_system.apply(operation_id, payload)
```

这段是控制逻辑示意。在并发条件下，“先查后写”仍有竞争，真实下游需唯一约束或原子幂等 API。恢复执行前也要确认参数与原 operation_id 一致。

降级可以选择只读、缩小任务范围、转人工或暂停接收，不应无提示地跳过验收。Kubernetes 的[Deployment 回滚](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)处理部署修订，外部业务补偿需要额外设计。所有本地验证范围见[代码与报告](../05-code/README.md)。
