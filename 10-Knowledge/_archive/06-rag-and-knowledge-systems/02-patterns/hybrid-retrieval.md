# Pattern：Hybrid Retrieval

> 状态：draft

## 问题

单一向量检索能覆盖自然语言语义，却可能混淆编号；单一 BM25 或关键词检索能命中术语，却可能漏掉同义表达。领域查询经常同时包含两类信号。

## 适用条件

- 语料同时包含自然语言与标识符、型号、命令或版本；
- 用户表达与文档术语不完全一致；
- 错误召回相似编号会带来实际风险；
- 有标注查询集可以校准融合和重排。

## 方案

1. 从原始 Query 保护性提取精确实体。
2. 在权限、产品、版本和时间范围内并行检索。
3. 使用 Dense、Sparse 和 Exact 通道覆盖不同召回需求。
4. 合并候选，按来源和位置去重。
5. 采用经过验证的加权融合、RRF 或 Query Routing。
6. 对候选集 Rerank，并做版本冲突与多样性处理。
7. 保留通道、分数、来源和位置，供 Context 与 Eval 使用。

## 不变量

- 精确实体不能在 Query 改写中丢失。
- ACL 和作用域过滤不能由生成模型补救。
- 融合分数只表示排序信号，不表示事实正确概率。
- 相关文档不等于支持具体主张，引用仍需验证。
- 参数必须绑定数据集和版本，不能跨项目照搬。

## 代价

- 多套索引、更新与监控链路；
- 额外检索和 Rerank 延迟；
- 分数校准、去重和版本冲突处理更复杂；
- 需要分层标注与消融评测。

## 不适用

- 数据全部是结构化精确查询，数据库即可完成；
- 语料规模很小，直接搜索或完整读取更可靠；
- 没有真实查询和验证集，却希望通过复杂融合“自动变好”。

## 验证

比较单通道、简单 Union、融合和 Rerank 的 Recall@k、硬负例、端到端成功、延迟与单次成功成本。按编码类、自然语言类、版本类和歧义类 Query 分切片报告。

详细机制见：[混合检索与重排](../01-concepts/02-hybrid-retrieval-and-reranking.md)。

## 最小实现与扩展顺序

从[工程](../05-code/rag-pipeline-python/README.md)运行三条基线：`mode="bm25"`、`"exact"`、`"hybrid"`。本仓 hybrid 先融合已经实际实现的 BM25 与 Exact；只有显式配置 embedder 才增加 dense 通道。没有配置时 `mode="dense"` 报错，不会偷偷生成随机向量。

实验保留 `airflow obstruction` 对中文“风道堵塞”的失败。修复可以选择领域术语映射或真实跨语言模型，但应在独立查询上检验，避免只给这一道题硬编码答案。优化时同时查看噪声片段：Recall 提高但上下文填入大量不相关内容，也可能让最终答案更差。
