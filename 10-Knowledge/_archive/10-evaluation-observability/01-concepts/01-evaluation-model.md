# 评测对象与系统模型

> 状态：draft。本文的数字分别标明教学演算与现有确定性实验；不把离线脚本成绩当成真实模型成绩。

你让 Agent 写一份 Pine SDK 升级清单，它回答：“已经完成，三项变化都有引用。”打开目录，却没有清单文件。这时到底是谁判断任务成功：模型的最后一句话，还是检查磁盘的程序？如果下一步还要把清单交给另一个 Agent，误判一次就会把错误继续传下去。

再看一个更隐蔽的情况：文件存在，三项变化也齐全，但超时配置引用的是废弃预览稿。判断“文件存在”只能挡住第一种失败，挡不住第二种。评测要做的第一件事，就是把“完成”拆成能查证的条件，然后让检查结果与模型自述分开。

## 当前结果能否继续，与系统整体有没有进步

**运行中的 Evaluator** 处理眼前这一次结果。它读刚生成的清单，发现超时字段引用了 `preview.md`，返回“正式版引用缺失”。在支持验收反馈的循环中，可以据此再读 `v2.md` 并修正；若预算已经耗尽，就明确结束为未通过。Evaluator 不一定是另一个模型，检查文件、字段和引用的普通 Python 函数就能完成很多工作。

**离线 Evals** 处理一组任务和系统版本。比如修改了上下文压缩规则，要知道它是否减少漏引用，同时有没有让别的任务漏掉关键值，就要让旧版、新版分别运行同一批题，逐题比较。一次任务通过只能说明这次通过；不能据此断言系统整体更可靠。

两者可以复用同一个引用检查函数，但使用位置不同。运行中检查失败，可以触发修正；离线验收则记录最终结果。如果每轮执行都提供评分反馈，反馈本身也是任务条件，应写进配置，不能把有反馈与无反馈的系统混着比较。

## 核心组件

围绕上面的清单任务，我们自然会需要下面几个名字：

| 你手里实际拿着什么 | 名称 | 本例内容 |
| --- | --- | --- |
| 给系统的一道题 | Task | v1/v2 文档、清单要求、初始目录与验收规则 |
| 从干净目录运行一次 | Trial | 任务第一次执行；重置后再执行是第二次 Trial |
| 执行结束留下的事实 | Outcome | 实际清单内容、引用、输出目录，而非“已完成”这句话 |
| 执行中发生过的事 | Trajectory／Trace | 读了哪个文件、裁剪了什么、写了什么、哪里报错 |
| 检查某一要求的函数 | Grader | 文件是否存在、引用是否正确、字段是否齐全 |

一个任务可以有多个 Grader。文件存在通过、引用检查失败，最终仍然不通过；同时保留分项结果，才能知道该修哪一块。开放式报告可引入人工或模型评分，但可直接验证的事实仍应交给代码。答案措辞不同而含义等价时，也不该用全文逐字匹配误判。

**Agent Harness** 负责让被测 Agent 调模型、执行工具、维护状态；**Evaluation Harness** 在外面准备题目、重置环境、运行 Trial、收集结果和评分。一组固定任务就是 Evaluation Suite。它们是职责名，同一个工程可以同时包含两者。[Anthropic 的评测说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)采用了类似的任务、运行与结果区分。

## 在代码中把被测系统和评分器分开

完整 SDK 清单比较长。先把“嘴上完成，实际没做”的问题缩成一个计数器任务：输入要求加 1，初始值为 0，最终必须为 1。以下使用本库真实接口；进入[配套工程](../05-code/eval-harness-python/README.md)，设置 `PYTHONPATH=src` 后可运行。

```python
from eval_harness import EvalTask, run_suite, summarize

task = EvalTask(
    "increment",
    input={"delta": 1},
    fixture={"count": 0},
    expected={"output": {"ok": True}, "state": {"count": 1}},
)

def claims_done(request, state, emit):
    emit("claimed_complete")
    return {"ok": True}

def actually_done(request, state, emit):
    state["count"] += request["delta"]
    emit("updated", count=state["count"])
    return {"ok": True}

for system in (claims_done, actually_done):
    results = run_suite([task], system, trials=2)
    print(system.__name__, results[0].state, summarize(results)["trial_success_rate"])
```

两行应分别显示 `{'count': 0}, 0.0` 与 `{'count': 1}, 1.0`。两个函数返回相同的 `ok=True`，差异来自最终状态。每次 Trial 都深拷贝初始 fixture，所以正确版本跑两次后，每次结果都是 1，不会第二次变成 2。**fixture 是实验准备的初始环境，不是模型生成的答案。**

[runner.py](../05-code/eval-harness-python/src/eval_harness/runner.py)只把公开输入、可变环境与事件函数交给被测系统，`expected` 留在评分侧。这个参数边界减少无意泄漏，但同一 Python 进程不构成安全隔离。执行不可信生成代码时，还需要独立进程或容器及访问限制。

## Outcome 优先，Trajectory 用于解释与约束

结果验收先回答“做成了什么”。文件任务检查真实文件，数据库任务检查最终记录，代码任务运行指定测试。随后再看执行过程，解释失败，并检查是否走了不允许的路径。比如结果正确，却把其他租户的数据也读了出来，仍可能违反任务要求。

对于漏引用，先确定最终清单确实缺少引用，再沿 Trace 查：没检索到原文、检索到了但被裁掉、原文进入模型后生成时漏掉，是三种不同原因。不能仅从最后的错误答案判断模型能力差。Trace 记录工具调用、可见结构化决定和状态变化即可；不要求供应商未提供的隐藏推理过程。

## 成功率怎样计算，失败应不应该留在分母

下面是**教学演算，不是仓库实测**。两道任务各跑两次：A 的两次都成功；B 一次验收失败、一次抛出异常。总共 4 次 Trial，成功 2 次，所以成功率是 `2 / 4 = 50%`。把异常删掉会得到 `2 / 3`，但系统并没有因此变好。

故障原因可以分开报告：B 的异常可能来自外部连接，另一条可能来自模型漏项。按事先定义的全任务完成率，两个都没有交付，仍进入分母。若模型根本没配置、整组实验没有启动，则应写“未运行”，不能画成 0% 或捏造结果。

这里还要区分评分规则与程序已经具备的能力。配套 `run_suite` 能捕获同步函数抛出的 `Exception`，但没有超时终止、进程崩溃补记功能。函数如果一直卡住，它不会自动生成一条超时记录。要让超时和崩溃也留在分母，需要外层监督程序先登记计划执行的任务，再在截止时记录未完成状态；本篇末尾的超时题练习的是计算规则。

重复次数不一致时，也要说清平均方式。A 跑 8 次全成功，B 跑 2 次全失败：按 Trial 平均是 `8/10=80%`；先算每道 Task 的成功率再平均，是 `(100%+0%)/2=50%`。前者更受多跑的题影响，后者让每道题权重相同。配套 `summarize` 同时提供两种指标。

## 真正评测的是什么

复现实验需要固定整套系统：代码提交、模型与版本、推理参数、提示词、工具、上下文构造方式、数据版本和环境。只记“模型 A 得 80 分”，无法解释下一次为什么只有 60 分。

还要分开保存运行来源。Mini Agent 的 `demo` 有预写动作和答案字段，适合验机制；`live` 才是真实模型决策。即使用同一个 Grader，也不能合并成模型成功率。本篇配套 Harness 更简单：默认调用确定性 Python 函数，没有调用模型。重复运行用于检查环境重置，不是对模型随机性的独立采样。

具体到 [Mini Agent 的验收实现](../../../../20-Projects/00-mini-agent/mini_agent/evaluate.py)，内容检查读取 `report.json`，对 `report.md` 只检查文件存在；不能把通过 JSON 验收理解为 Markdown 正文已被逐项核对。课程完成表中，故意制造错误引用的实验显示 PASS，表示系统成功拒绝了错误结果；那次错误任务本身仍应为 FAIL。

## 能力、回归与风险不是同一个套件

想知道系统还不会什么，可以使用较难的能力题；想知道修改有没有破坏已有功能，需要固定的回归题；担心越权，要专门放权限与对抗输入；想测稳定性，同一任务需要多次真实运行。线上监测则观察实际用户分布，不能用四道教学题替代。

## 评测层次

先对解析、引用检查、工具参数做组件测试，再检查单 Agent、交接与恢复，最后运行端到端任务。组件测试容易定位问题，端到端结果更接近用户价值，两者应配合。验收也要允许合法替代实现：用户要正确清单，并没有要求工具必须按参考轨迹一模一样地调用。

## 好评测的属性

用刚才的例子自检：是否真的读磁盘而非听自述，决定它是否测到了需求；相同 fixture 能否重建，决定结果是否可复现；能否识别“文件存在但引用错误”，决定评分是否有区分度；失败能否定位到具体条件，决定分数有没有修复价值。

## 检查自己是否理解

**练习一：** 把计数器 Task 的 `expected.state` 删除，只保留 `ok=True`，假完成函数会怎样？参考解释：会通过。系统行为没改，评分器失去了独立检查；这叫验收缺口，不能当能力提升。

**练习二：** 10 次运行中 6 次成功、2 次验收失败、2 次超时，应报告多少？参考解释：预先约定的任务完成率是 60%，另外单列超时率 20%。不能删掉超时后声称 75%；若分析“已完成调用中的内容正确率”，应另起指标并明确分母是 8。
