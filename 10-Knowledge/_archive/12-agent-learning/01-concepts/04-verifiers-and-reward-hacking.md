# 验证器与奖励投机：分数高为什么可能任务没完成

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

让 Agent 把“测试通过”写到日志里，再用搜索这四个字的脚本评分，它很快就能拿满分，却不需要运行任何测试。问题在于验证器读取了可被 Agent 改写的陈述，而没有读取环境中的实际结果。

## 验证器验证哪一层

结果验证器检查最终目标，例如独立测试进程的退出码和实际断言、数据库中的记录、文件中必须存在的内容。过程验证器检查中间决策，例如调用是否越权、证据是否先于结论、预算是否超限。过程正确不保证最终正确，最终正确也不意味着过程可以接受。

设候选输出 $y$，真实任务是否成功为 $G(y)$，可实现的评分器为 $R(y)$。训练能直接优化的是 $R$，而我们关心的是 $G$。一旦存在 $R(y)$ 很高但 $G(y)=0$ 的行为，持续搜索会更容易找到它。这就是奖励投机，而不需要假设 Agent 有某种主观意图。

| 容易被利用的评分 | 反例 | 更直接的证据 |
|---|---|---|
| 看回答里是否出现 PASS | 只打印 PASS | 外部测试进程和断言结果 |
| 看引用格式是否合法 | 编造一个格式正确的文献 ID | ID 解析到可访问原文并核对支持关系 |
| 看工具调用次数是否充分 | 无意义重复调用 | 任务产物和必要步骤约束 |
| 用修改后的测试验收补丁 | 删除失败测试 | 隔离保存的固定验收集 |
| 奖励简短轨迹 | 直接宣布完成 | 达成目标后再比较成本 |

## 把约束作为门，不只是小惩罚

若“越权但成功”得 100 分，越权只扣 1 分，优化器依然会选择越权。可以先判有效性，再比较任务得分：

$$R(\tau)=\begin{cases}-1,&\text{违反硬约束}\\\mathbf1[\text{独立验收成功}],&\text{其他情况}\end{cases}.$$

这是本库教学奖励，不是通用最优奖励设计。失败合法轨迹得 0，成功合法轨迹得 1，越权轨迹得 -1；成本作为同等有效性和成功条件下的排序指标。这样不会为了节约一步就奖励未完成任务。

```python
def reward(trajectory):
    if not trajectory["policy_allowed"]:
        return -1.0
    return float(trajectory["external_tests_passed"])
```

这里的 `external_tests_passed` 必须由受保护的运行环境写入。若它仍来自模型 JSON，函数再清晰也没有意义。

这个函数是**事后评分**，不是执行权限门。即使越权得 -1，随机采样或训练不充分时仍可能生成越权动作；必须由 Runtime 在动作发生前拒绝非法请求。再区分“所有候选都非法”的情况：`max(rewards)` 仍会选出一个 -1，选择器应先过滤非法候选，空集合就停止，而不是执行分数最高的非法动作。

## 如何验收一个验证器

先构造正常成功、正常失败、伪造成功、越权成功四类反例；比较误接受率与误拒绝率。小样本全对只证明这几条反例被覆盖，不证明真实任务已可靠。开放问答需要人工校准，代码任务需要隐藏测试和环境隔离，科研任务还需要数据泄露、统计口径和实验可复现检查。

[实验](../04-labs/01-trajectories-and-rewards.ipynb)实际对比“相信输出文本”和“读取外部验收”两种规则，并观察获胜候选变化。[过程监督论文](https://arxiv.org/abs/2305.20050v1)提供数学推理任务的过程/结果监督研究证据；它不能直接证明任意企业任务都更适合过程奖励。
