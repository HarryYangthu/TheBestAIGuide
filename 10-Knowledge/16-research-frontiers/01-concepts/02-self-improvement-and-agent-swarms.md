# 自改进与群体协作：究竟改了什么，改进由谁证明

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

> 研究快照：2026-09-06；以下是代表方法的机制对照，不是能力排行榜。

Agent 在失败后写一段反思，不等于系统已经变好。改进至少包含一个可保存的变化，以及在独立任务上证明收益的验证。先区分变化发生在哪里，才知道怎么评测。

| 方法 | 改变的对象 | 可保留的产物 | 最容易混淆的结论 |
|---|---|---|---|
| 自反思 | 下一次上下文 | 错误总结 | 多写反思不等于学到正确经验 |
| Trace-to-Skill | 可复用程序或操作说明 | 技能及适用条件 | 同任务复用不等于跨任务泛化 |
| Prompt/工作流搜索 | 系统提示与控制流程 | 版本化配置 | 在开发集调优不等于测试集提升 |
| 权重更新 | 模型参数 | 权重、数据和训练配置 | 记忆写入不是参数训练 |
| 多 Agent 协作 | 任务分配与信息合并 | 候选、证据和合并结果 | 更多发言不等于独立证据 |

## 从反思到可用经验

[Reflexion v1（2023-03-20）](https://arxiv.org/abs/2303.11366v1)研究用动态记忆和反思改善后续行动。工程上可以把“失败原因—触发条件—替代动作—来源任务”保存为候选经验。验收前不要把它提升为全局规则：一个任务上“多重试一次”有效，另一个任务可能造成重复写入。

经验进入技能库前需要正例与反例。正例验证在适用条件下完成任务；反例验证条件不满足时不触发。例如“提交超时后查询请求状态”适合下游提供可查询请求 ID 的接口；没有该接口时应报告不确定，而不是凭空构造状态。

## 多数票为什么可能一起错

三个 Agent 读同一份错误资料并使用同一个模型，可能一致给出错误答案。只有在错误足够独立、单体正确率高于随机等假设下，多数票才有特定统计优势。对于三个独立、同正确率 $p$ 的二分类判断，多数正确率是 $p^3+3p^2(1-p)$；$p=.7$ 时为 .784。错误完全相关时仍是 .7。

```python
p = .7
independent_majority = p**3 + 3*p*p*(1-p)
assert abs(independent_majority-.784) < 1e-12
```

改善协作的方向是让子任务、证据来源或验证方法产生实质差异，并要求每条结论附证据。独立读资料、运行不同测试，比让同一模型扮演三个性格更有可解释的分工。AutoGen 的[早期框架论文 v1](https://arxiv.org/abs/2308.08155v1)展示多 Agent 对话式组合，不证明任意任务都优于单 Agent。

## 自修改的验收边界

自修改代码只能改变待评估候选版本，不能同时修改最终测试答案和通过门槛。把补丁放隔离分支，记录原版、新版、预算和逐题差异；收益成立后再提升版本。[研究算例](../05-code/research_checks.py)只运行概率对照，技能系统参考[Voyager v1](https://arxiv.org/abs/2305.16291v1)。本库未宣称已经构建自动自进化系统。
