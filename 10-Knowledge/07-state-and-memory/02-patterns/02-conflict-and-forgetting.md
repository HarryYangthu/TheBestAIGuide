# 冲突、过期与遗忘：避免旧事实悄悄回来

> 状态：draft | 来源核验：2026-09-06

A用户之前偏好Python，今天说这次课程使用TypeScript。这里首先要判断语义：是“这次课程”的临时约束，还是“以后都换语言”的长期偏好更新？前者写入当前任务State，后者才更新Memory。时间较新本身不能替代作用域判断。

| 情况 | 合适动作 | 不应做什么 |
| --- | --- | --- |
| 同事实重复出现 | 去重或附加来源 | 每次追加成一条独立高权重记录 |
| 主体明确更新偏好 | 按版本更新，保留来源 | 根据模型猜测覆盖用户原话 |
| 两个可信来源冲突 | 保存冲突与适用条件，必要时询问 | 自动选措辞最肯定的一个 |
| 信息超过有效期 | 读取时排除，必要时重新查询 | 仅因向量相似就继续使用 |
| 用户撤回或删除 | 从活动存储与召回链路清除 | 只删除主表却保留缓存摘要 |

## 为什么过期检查放在读取路径

定时清理可能延迟一分钟，但一分钟内过期事实也不该进入模型。本例读取条件为`expires_at > now`，因此在到期时间点立即不可见；后台清理只负责回收空间，不承担正确性。没有TTL的偏好仍需接受主体更新或删除，不能把“无到期时间”解释为永久正确。

```python
m = store.put("alice", "context_budget", 8000, "task:1", now=100, ttl=10)
assert store.get("alice", "context_budget", now=109) is not None
assert store.get("alice", "context_budget", now=110) is None
```

## 版本冲突不能用无限重试解决

两个写入者都基于版本1产生不同值，只有一个能成功写成版本2。另一个应重新读取证据并决定是否合并。自动读取新版本再无条件覆盖，会绕过CAS原本保护的业务语义。CAS保证你知道自己基于哪个版本写入，不能决定哪个事实正确。

本库`put`默认预期版本0，表示创建新记录；更新须显式传旧记录的版本。过期记录仍占有其键和版本，避免旧任务把同名事实当全新记录复活。需要更新时由可信业务层在保留的版本和当前证据基础上提交，示例不提供对模型开放的任意覆盖接口。

过期后的 `get` 返回 `None` 是“当前不可使用”，不等于“存储从未存在”。不要随后直接 `put` 当新记录创建：它会因预期版本 0 与保留版本不一致而失败。进阶工程的 [MemoryAssistant.remember](../../../20-Projects/learning-workbench/src/learning_workbench/memory.py)在收到新的明确长期偏好后，由可信业务层读取保留版本，再做受 CAS 保护的更新；读取和写入之间仍可能冲突，调用方应处理冲突。

## 删除为何保留墓碑

`forget(subject,key)`清空活动记录中的value/source，增加版本，标为deleted。保留键与版本的这部分元数据叫墓碑。它防止一个旧写入者带着删除前版本又把数据写回来。删除后`get/retrieve`均不可见，重复删除无副作用。

这只保证应用读取路径不再返回内容。SQLite页面、备份、日志或另一个系统的向量索引仍可能保留旧数据；真正的清除必须明确覆盖这些副本的保留期限与操作。本例不把逻辑删除描述为磁盘安全擦除，Checkpoint历史也需独立的保留/删除策略。
