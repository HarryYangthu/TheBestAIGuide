# SLO 与成本：服务可用和任务成功是两种指标

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

API 每次都返回 200，但 Agent 经常生成错误报告，这个系统的接口可用，任务却不可靠。分别测基础设施和业务结果，才能判断应该修服务还是改模型/数据。

## 指标口径先于数字

SLI 是测量值，SLO 是目标。任务成功 SLI 可以定义为“在指定截止时间内通过独立验收的任务数 / 合格任务总数”。合格任务、取消、用户缺资料、服务拒绝和超时如何计入，要提前规定，不能事后把失败排除。

| 指标 | 起止点与分母 | 它回答的问题 |
|---|---|---|
| 接口可用率 | 合法 API 请求中的可服务比例 | 能否接入系统 |
| 任务成功率 | 符合范围任务中的验收成功比例 | 能否完成工作 |
| 首个可用事件时延 | 请求到有效进展事件 | 用户是否得到及时反馈 |
| 完成时延 | 创建 Run 到终态 | 整项工作要多久 |
| 单位成功任务成本 | 所有相关花费 / 成功任务数 | 为成功付出多少资源 |

平均时延掩盖长尾，因此同时报告分位数和样本数。不同任务类型应分层统计，避免“简单任务增多”造成总体成功率虚高。

## 错误预算怎么计算

若月内合格任务数 $N=10000$，目标 $s=0.99$，允许失败预算 $B=N(1-s)=100$。已经失败 70 次，剩余 30 次。实际失效率为 $e$ 时，燃烧率为 $b=e/(1-s)$；例如最近窗口失败率为 5%，燃烧率就是 5，表示按当前速度消耗预算比允许速度快 5 倍。只有窗口、任务分布和分母定义一致时才可比较。

```python
from decimal import Decimal
n, slo, failed = 10000, Decimal('0.99'), 70
budget = Decimal(n) * (1 - slo)
remaining = budget - failed
assert remaining == 30
```

暂停发布还是继续修复，需要预先定义错误预算政策。不要用一个极短、样本很少的窗口自动阻断所有工作；可以结合短长窗口和最小样本量。

## 便宜模型可能更贵

$$C_{\rm success}=\frac{C_{\rm model}+C_{\rm tools}+C_{\rm compute}+C_{\rm storage}}{N_{\rm passed}}.$$

假设方案 A 完成 100 个任务花 20 个成本单位、成功 50 个，则每个成功任务为 .4；方案 B 花 30、成功 90 个，则为 .333。B 单次更贵却更有效。数字只是教学算例，见[可运行脚本](../05-code/production_checks.py)。如果所有任务失败，分母为零，应报告无成功与总花费，而不是显示成本 0。

进一步比较人工接管时间、用户等待和机会成本，但不要把估算值混成实测财务收益。来源：[Google SRE 的 SLO 方法](https://sre.google/workbook/implementing-slos/)和[错误预算政策](https://sre.google/workbook/error-budget-policy/)。[发布篇](03-release-and-recovery.md)说明指标如何进入实际门禁。
