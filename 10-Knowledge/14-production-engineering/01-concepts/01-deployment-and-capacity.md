# 部署与容量：并发 Agent 为什么会把系统拖慢

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

单个 Agent 用 30 秒完成任务，并不意味着开 100 个就能每秒完成 3 个。模型配额、工具并发、浏览器内存、队列和数据库可能分别成为瓶颈，且重试会增加实际流量。

## 先拆开入口、执行和模型服务

API 接收请求并创建 Run，队列缓冲到达波动，Worker 执行工具和模型请求，模型服务单独处理推理，状态和产物进入持久存储。轻量同步问答可以不引入队列；长任务、浏览器、代码执行需要独立生命周期。代码执行容器和浏览器实例不应与 API 主进程共享无隔离的工作目录。

容量要按资源类型计量：每秒请求、每分钟 token、同时运行的浏览器数、GPU KV cache、数据库连接数。把所有限制合并成一个“最大并发”会导致某类重任务占满资源。

## 一个可算的容量估计

在稳定系统中，Little 定律为 $L=\lambda W$：$L$ 是平均系统内任务数，$\lambda$ 是平均到达率，$W$ 是平均停留时间。若每秒到达 2 个任务，平均停留 30 秒，平均在途任务就是 60 个。这是平均关系，不保证 P99，也不能用不稳定积压的数据直接规划容量。

对于占用一个 Worker 的任务，若单任务平均服务时间为 $S$，有 $c$ 个 Worker，则服务能力粗略为 $\mu=c/S$。当 $\lambda\ge\mu$，队列长期增长；即使略低于它，突发流量和长尾仍会使排队时延变差。

```python
arrival_per_second, service_seconds, workers = 2, 30, 40
capacity = workers / service_seconds
assert arrival_per_second > capacity   # 积压是必然，不是模型偶然变慢
```

## 五类拥塞与对应处理

| 瓶颈 | 信号 | 可采取的动作 | 不能忽略的代价 |
|---|---|---|---|
| 模型限流 | 429 与 token 配额占用 | 分模型令牌桶、延迟入队 | 首次响应更慢 |
| Worker 饱和 | 等待时间上升 | 限制并发、扩容、拒绝超额任务 | 扩容可能撞上模型上限 |
| 大上下文显存占用 | OOM、KV cache 紧张 | 输入预算、分级队列 | 压缩可能损失信息 |
| 浏览器泄漏 | 常驻实例数持续增长 | 生命周期关闭与实例配额 | 冷启动成本 |
| 重试风暴 | 下游失败时流量反增 | 重试预算、退避抖动、熔断 | 部分任务提前失败 |

队列要有最大长度、最长等待和过期策略，否则“成功接收所有请求”只是把故障推迟。停机时先停止领取任务，再在期限内完成或记录可恢复状态；滚动部署新 Worker 之前要检查旧任务状态格式是否兼容。生产原则参考[Google SRE 过载处理](https://sre.google/sre-book/handling-overload/)，容器发布语义参考[Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)。本篇没有将容器重启等同于任务恢复。
