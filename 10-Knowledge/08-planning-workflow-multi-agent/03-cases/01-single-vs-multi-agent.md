# 同一任务：确定性程序、单 Worker 与并行 Worker 的对照

> 状态：draft；来源核验：2026-09-06；配套实现已进行本地 fixture 验证，非真实模型性能评测。


这个案例要回答一个具体问题：把候选评审拆给两个 Worker，是否值得？输入完全相同，输出标准也相同；先看运行结果，再决定架构。

## 输入与唯一验收标准

以下为教学构造数据，不是真实模型测试结果。目标是在时延不超过 20 ms、内存不超过 220 MB 的候选中选择质量最高者。

| 候选 | quality（越高越好） | latency_ms | memory_mb | 是否可行 |
|---|---:|---:|---:|---|
| A | 0.91 | 18 | 200 | 是 |
| B | 0.93 | 29 | 150 | 否，时延超限 |
| C | 0.88 | 12 | 90 | 是 |

答案应为 A。B 分数虽高，但不在可行集合中。验收不是“回答看起来有道理”，而是 `selected == "A"` 且没有缺失评审。

## 三个执行方案

1. 确定性基线直接筛选表格再取最大值，模型调用数为零。
2. 单 Worker 顺序模式先获取质量映射，再获取可行集合，随后选择；同时只有一个任务运行。
3. 双 Worker 并行模式让这两步同时运行，最后执行同一个选择函数。

这里的“单 Worker”是 Agent 执行结构的无模型替身，不是经过真实 LLM 测试的单 Agent。当前 Worker 只读取 fixture 并异步等待 20 ms，模拟独立 I/O 操作。这样可以把调度正确性和语言模型能力分开验证。要评价真实多 Agent 的效果，应保持此契约，替换 Worker 内部实现并增加任务样本、模型版本和 Token 成本记录。

## 实际证据在哪里

[Notebook](../04-labs/01-single-vs-multi-agent.ipynb)保存了三种模式的输出和真实运行事件；[experiment.json](../04-labs/artifacts/experiment.json)保存结构化 trace。串行与并行都应选择 A，最大活跃 Worker 数分别为 1、2；两者都执行两次 Worker 调用。确定性基线直接得到 A。

耗时随机器变化；本实验不设置一个过于脆弱的“必须快 2 倍”测试。验证的硬条件是并发上界与结果一致性。若测得并行更快，其原因是两个独立的等待重叠，而非“多个 Agent 更聪明”。在这个数据齐全的任务上，确定性基线最简单，额外的 Agent 决策没有被证明必要。

## 三个故障怎么改变结论

| 注入条件 | 观察结果 | 系统应该如何处理 |
|---|---|---|
| 约束 Worker 超时 | 质量结果保留，missing_tasks 非空 | 显示部分结果，拒绝最终选择 |
| 两个 Worker 给 decision 不同值 | 合并抛出 MergeConflict | 追查证据与规则，不能后写覆盖 |
| 外部取消主任务 | 子 Worker 收到取消并退出 | 向调用方传播取消，不继续后台工作 |

这些路径在[测试](../05-code/multi-agent-runtime-python/tests/test_runtime.py)中实际执行。取消是协作式的：本例 Worker 在 `await` 处接受取消；如果真实 Worker 使用阻塞 CPU 循环或忽略取消，Python 协程层不能强制停止它。需要进一步使用进程或远端任务的取消接口。

## 把案例迁移到自己的系统

先保留候选 ID、评审输出和最终验收函数，再将 `quality_worker` 替换成模型评估或实验查询，将 `constraint_worker` 替换成硬件测量读取。新增一个 Worker 必须说明它提供了什么独有证据。用同一任务集比较任务成功率、合法完成率、成本和时延，不只报告最成功的一条演示轨迹。
