# 多 Agent 拓扑：先确定谁拥有决策权

> 状态：draft；来源核验：2026-09-06；配套实现已进行本地 fixture 验证，非真实模型性能评测。


“研究员、工程师、评审员”是角色名字，名字本身不会形成协作。真正决定系统行为的是：谁分配任务，谁能调用哪些工具，谁持有最终状态，意见冲突时谁作决定。

## 从控制权选择拓扑

| 拓扑 | 谁决定下一步 | 适合的任务结构 | 最常见的失效 |
|---|---|---|---|
| Router 路由 | 路由器选一个处理者 | 问题类别明确、只需一个专家 | 分类错误后没有回退 |
| 固定并行 Worker | 程序预先给定分工 | 子问题独立，可分别验收 | 多个结果互相覆盖 |
| Supervisor 主从 | 主 Agent 根据结果继续委派 | 子任务会随调查过程变化 | 主节点拥塞、反复委派同一件事 |
| Planner–Executor | 规划者列步骤，执行者完成 | 计划可显式检查、动作受约束 | 计划已失效，执行者仍照旧运行 |
| 同行讨论与投票 | 协议决定轮次和采纳方式 | 存在不同可辩论的假设 | 相同模型共享偏差，投票放大错误 |

这些方式可以组合。例如先用 Router 选择“科研任务”，再由 Supervisor 分配文献和实验评审，最后用确定性约束检查结果。但每增加一级，都要解释它比直接调用 Worker 多解决了什么。

## 并行什么时候真能省时间

假设两个独立任务各耗时 \(t_1,t_2\)，调度和汇总合计开销为 \(h\)。串行用时约 \(T_s=t_1+t_2\)，并行用时约 \(T_p=\max(t_1,t_2)+h\)。只有 \(h<\min(t_1,t_2)\)，并行才可能更快。

例如各 2 秒、协调 0.4 秒，串行 4 秒，并行 2.4 秒。若其中一个任务只需 0.1 秒，协调仍为 0.4 秒，并行反而不划算。这个算例假设任务独立、资源充足；共享模型限流或 GPU 时，两个请求不一定真正并行。

[实验](../04-labs/01-single-vs-multi-agent.ipynb)用两个 20 ms 异步等待模拟 I/O，记录实际最大并发和事件耗时。它只能证明调度器实现了并发，不能推断多模型合作会提升推理能力。

## 多数票为什么不是可靠性保证

若 \(n\) 个二分类评审独立且每个正确概率为 \(p\)，奇数 \(n\) 的多数正确率为

\[
P_{vote}=\sum_{k=(n+1)/2}^{n}\binom nk p^k(1-p)^{n-k}.
\]

例如 \(n=3,p=0.7\)，得到 \(3\times0.7^2\times0.3+0.7^3=0.784\)。但真实 Agent 常用同一模型、同一检索材料和近似提示，独立性假设不成立。若三者总是同错同对，投票仍只有 0.7。需要记录各自依据和错误相关性，不能拿理想公式充当系统实测。

候选模型选择更适合“证据+约束”而非无条件投票。A 的时延为 18 ms、B 为 29 ms，预算为 20 ms，无论多少评审喜欢 B，都不能让它通过硬约束。投票可以比较可行候选的软性偏好，不能改变测量事实。

## 本库实现到哪一层

[Router](../05-code/multi-agent-runtime-python/src/multi_agent/router.py)按任务类型找到异步 Worker；[Supervisor](../05-code/multi-agent-runtime-python/src/multi_agent/supervisor.py)限制并发、期限与任务数；[合并器](../05-code/multi-agent-runtime-python/src/multi_agent/merge.py)检查输出冲突。Worker 是可替换接口，当前接入的是确定性教学函数。接入真实 Agent 时，让函数内部调用 Agent Loop，再返回同一契约即可；不要让它直接改主状态。
