# 任务契约与交接：让接手的人知道要带回什么

> 状态：draft。以虚构的 Pine SDK 升级任务解释协作；文中的消息包是教学设计。现有代码的字段、行为和未实现部分分别说明，避免将设计当成已运行能力。

主 Agent 请两个 Reader 分别研究 Pine SDK 的 v1 和 v2。第一个返回“旧版使用 API Key”，第二个返回“新版更安全，建议升级”。它们都像是做了事，但主 Agent 无法据此填写超时与重试的比较项，也不知道“更安全”来自哪一行。

把任务换成“只读 `v2.md`，提取认证、超时、重试三项原文和行号；找不到就报告缺失，不补写”，结果就容易接上。**任务契约**就是双方对输入、允许动作、交付物和完成条件的约定。它的作用是让接手的人少猜，也让接收方知道怎么检查。

## 先看一次委派实际做了什么

Mini Agent 已有[两个 Reader 的实现](../../../20-Projects/00-mini-agent/mini_agent/subagents.py)。宿主固定分配 `v1.md` 和 `v2.md`，每个 Reader 创建自己的模型对象、消息列表与四轮循环；可用工具只有 `read_file`。每次收到调用，宿主还检查路径必须等于分配给它的文件。模型即使请求读另一份资料，也拿不到对应结果。

Reader 返回自己的轨迹，宿主核对是否成功读过指定文件、是否正常结束，再写出回执。完整消息历史彼此独立，但两个 Reader 仍在同一个 Python 进程，不能把这种上下文隔离当成不可信代码的安全沙箱。

这里的 `delegate()` 像普通函数调用：调用方等待，拿到返回值，再决定下一步。另一种协作叫 **handoff**，本文用它表示“交出下一步决策的控制权”。例如主 Agent 发现需要用户确认迁移范围，转给迁移顾问继续与用户沟通；此时要记录谁负责后续对话、保留哪些上下文、何时结束或交还控制。只把文件发给另一个 Agent，不一定发生了控制权转移。

这一区别会影响失败后的责任。在委派中，父任务负责汇总和验收；在控制权交接中，接手方负责推进约定范围内的后续任务，运行时记录当前负责人。Mini Agent 目前实现的是固定委派并返回，尚未实现会话控制权切换。

## 同一个任务，为什么还需要几个不同的 ID

如果任务只在一个函数里完成，参数和返回值就够了。跨线程或跨进程以后，消息可能晚到、重发，接收方需要知道“这是哪件事的哪一次消息”。下面是给 Pine Reader 的说明性消息包，不是现有项目直接接收的 API：

```json
{
  "message_id": "msg-17",
  "call_id": "rpc-8",
  "task_id": "read-v2",
  "parent_task_id": "pine-upgrade",
  "attempt": 1,
  "input_version": "docs-rev-4",
  "kind": "delegate",
  "payload": {
    "path": "v2.md",
    "fields": ["auth", "timeout", "retry"],
    "output": "每项返回原文、路径、行号；缺失项单独列出"
  }
}
```

`task_id` 标识“读取新版资料”这件逻辑工作，即使执行重试，它仍是同一个任务。`attempt=1` 表示第一次执行尝试；真正重新执行时才加一。`message_id` 标识这一条业务消息，网络发送失败而重发同一内容时可以沿用，用于识别重复。`call_id` 只配对一次请求和响应，重发网络请求可以换一个新的调用 ID，而不意味着新开一次业务任务。

还有一种常见的 `tool_call_id`，它用来把工具结果对应回模型发出的某次工具调用。它也不是父任务 ID。不同实现字段名可以不同，关键是不要用一个 ID 同时承担这些职责。`input_version` 则回答另一件事：“这份结果基于哪一版资料？”任务相同但输入更新了，旧结果不能直接接着用。

假设第一条请求已被 Reader 收到，但回复丢失了。父任务重发 `msg-17`，换用 `rpc-9`，这仍是 attempt 1。Reader 应返回同一个任务的已知状态，而非重新创建一次读取。等确认第一次执行失败、准备再执行时，才创建 attempt 2 和新的业务消息。这样可以区分“没收到回复”与“工作需要重做”。

## 三次交接，各检查一层

委派之前，先检查任务 ID 是否重复、输入路径是否允许、总任务数是否超限，再把请求放进队列。收到“已接收”只证明对方接受了请求；收到“已开始”只证明开始了执行。它们都没有证明原文已经读到。

Reader 返回以后，先检查格式。例如结果中是否存在三个比较项、引用是否有路径与行号。这一层可以由 Schema 或普通代码完成。再去看内容：`v2.md:3` 是否真的写了默认 10 秒，`v2.md:4` 是否说明默认重试 0 次。格式齐全但引用预览稿的 5 秒，仍然是错误答案。

合并之前，还要检查任务是否收齐。下面代码使用本域已有接口，示范“v1 成功但 v2 尚未返回”时的实际行为：

```python
from multi_agent import WorkerResult, merge_results

results = [
    WorkerResult("read-v1", "ok", {"v1": {"timeout_seconds": 30}})
]
merged = merge_results(
    results,
    expected_task_ids=["read-v1", "read-v2"],
)
assert merged.values == {"v1": {"timeout_seconds": 30}}
assert merged.missing_tasks == ["read-v2"]
assert merged.complete is False
```

`expected_task_ids` 是出发前就确定的委派清单。没有它，合并器只能看到“一份收到的结果成功了”，无法推断还有一份根本没来。`complete=False` 允许展示已拿到的 v1 资料，但不能把整份升级报告标为完成。

这段示例数据只演示清单核对，没有验证 Pine 引用。实际 [merge_results](../05-code/multi-agent-runtime-python/src/multi_agent/merge.py) 还会拒绝重复任务结果和清单之外的任务结果；两份结果对同一字段给出不同值时，抛出冲突错误，避免“谁最后写入就听谁的”。v1、v2 应分别存放，然后由比较步骤解释差异，不能都写入一个没有版本含义的 `timeout` 字段。

## 为什么不给子 Agent 整段历史

Reader 需要任务范围、指定文件和输出要求，不需要主 Agent 早先讨论过的所有方案。让它看到废弃预览稿的长篇讨论，反而可能把 5 秒误记成正式值。输入裁剪的依据是“完成这个子任务需要什么”，并保留能追溯来源的信息。

本域的 [Supervisor](../05-code/multi-agent-runtime-python/src/multi_agent/supervisor.py) 在调用 Worker 前深拷贝 `payload`，避免一个 Worker 改动嵌套列表后污染其他任务。它只检查返回值是可序列化的字典、键集合符合约定，没有通用的事实检查或任意嵌套 Schema 校验。需要的领域检查应显式补进任务或验收步骤，不能靠 `ok` 这个名字猜测。

## 错误也属于交付结果

v2 没有重试说明，与读取 v2 时网络失败，是两种情况。前者意味着“成功读取，但资料缺一项”，可以请用户补资料；后者意味着“还不知道资料里有没有”，可以考虑重试。用一个空字典表示两者，父任务就无法选择正确动作。

当前基础运行时返回 `ok/error/timeout`，异常结果保留任务 ID 和错误原因。外部取消会传播取消异常，并等待子任务清理。业务上还可能需要 `blocked` 或 `input_required`，表示缺少前提或等待补充输入；增加状态时，要同步定义哪些状态允许重试、哪些允许合并。

## 消息晚到、重复和乱序时，怎样避免改坏结果

先看一个具体时间顺序。它是需要实现的控制规则，不是对当前 Mini Agent 的能力声明。

| 时间 | 收到什么 | 应采取的动作 |
|---|---|---|
| 1 | `msg-17`，读取 v2 的 attempt 1 | 登记消息与任务，启动一次读取 |
| 2 | 同内容的 `msg-17` 重发 | 返回已知状态，不新建任务 |
| 3 | attempt 1 超时，调度器授权 attempt 2 | 记录当前有效尝试为 2 |
| 4 | attempt 2 基于 `docs-rev-5` 返回 | 检查格式、引用和输入版本，通过后提交 |
| 5 | attempt 1 的旧结果迟到 | 保留为迟到记录，不覆盖第 4 步 |
| 6 | attempt 2 的“已开始”通知迟到 | 不让已完成状态退回运行中 |

第 2 步按消息 ID 去重，第 5 步按尝试和输入版本检查结果，第 6 步按状态转移规则检查事件。三者分别处理不同问题，单独加一个去重集合不够。如果同一个消息 ID 携带不同内容，应报错，不能悄悄当成重发。多个接收线程同时操作时，检查与登记还必须在同一把锁或同一事务里，否则两个线程都可能判断“没有处理过”。

不必一开始就引入复杂消息总线。本地项目可以先用函数调用、任务字典和明确的返回对象。等确实跨进程传输，再增加消息登记和结果版本检查。重发机制尤其不能被误认为“副作用恰好执行一次”；发邮件或写外部数据库还需要操作层的幂等设计。

## 跑一次，看看收到的到底是什么

先从仓库根目录运行现成的 Pine 委派实验，每次使用新的输出目录：

```bash
python 20-Projects/00-mini-agent/delegate.py --mode demo --output .runs/pine-handoff
```

打开 `delegation.json`：v1 和 v2 各一条回执，`read_observed=true`、`finished=true`，总结果 `passed=true`。再看两份 `v1.md.trace.json`、`v2.md.trace.json`：各自只有分配给自己的读取任务，每份包含一次读取调用和对应工具结果。可与[参考回执](../../../20-Projects/00-mini-agent/reference/subagents/delegation.json)对照。demo 的动作由脚本驱动，这个 PASS 只验证受限读取与结束，不验证自然语言总结正确，更不代表完整升级清单已经完成。

要观察实际 HTTP 消息，可以再运行：

```bash
python scripts/run_python.py -m learning_workbench.a2a_demo
```

这是项目的本地文本协议子集，读懂通信过程即可。示例内容临时换成 `DEMO-A limit=70 C`，不是 Pine 任务。终端先出现 `input-required`，重复首条消息仍返回同一个任务 ID；补充输入后变成 `completed`，接着查询任务、把产物发给第二个端点，最后另建一个待输入任务并取消为 `canceled`。

查看 [a2a_demo.py](../../../20-Projects/learning-workbench/src/learning_workbench/a2a_demo.py) 中 `messages` 的消息登记：同 ID 同内容返回已有任务，同 ID 不同内容报错。这是项目实现的去重扩展。示例 Worker 只是回传文本，不作事实审查；任务只存在内存中，重启后会丢失。它没有上表中的尝试版本控制，也没有完整分布式可靠交付。

练习一：v1 成功回传了两次，v2 一次都没有返回，系统共收到两条成功消息。能否完成？**参考答案：**不能按消息数量判断。按委派清单核对任务 ID，应发现 `read-v2` 缺失；重复的 v1 不能填补它。当前 `merge_results` 会直接拒绝重复结果。

练习二：Reader 返回 `completed`，引用的 `preview.md:3` 确实写着 5 秒。是否通过？**参考答案：**读取动作完成、引用位置存在，但输入范围和版本错误。应拒绝作为正式 v2 的证据，并要求读取 `v2.md:3` 的 10 秒。传输成功、执行完成、业务验收通过需要分别判断。
