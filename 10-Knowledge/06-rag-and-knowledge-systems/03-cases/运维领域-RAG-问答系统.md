# 运维领域 RAG 问答系统

> 状态：draft / design case
> 证据：现有方案笔记
> 未提供：原始数据、实现仓库、运行环境、标注集、实测指标

## 案例目标

把 PDF、Word、HTML 等运维资料转化为可检索、可追溯的知识，并针对自然语言现象、设备型号和故障码返回有来源的排障建议。

这是一份系统设计案例，不是已经完成验收的项目报告。文中的产品、模型和参数只记录原方案候选，不构成性能结论。

## 领域约束

运维知识同时具备：

- 自然语言表达多样，例如“风扇灯红了”和“风扇模块故障”；
- 故障码、型号、版本和命令要求精确匹配；
- 手册版本与设备范围决定答案是否适用；
- 排障步骤具有顺序、前置条件和风险；
- 错误建议可能产生真实系统副作用；
- 答案需要引用原文，便于工程师复核。

因此系统不能只做向量相似度搜索，也不能在没有证据时继续生成确定答案。

## 设计架构

```text
PDF / Word / HTML
  -> Parse + Normalize
  -> 保留标题、页码、表格、步骤和来源
  -> 抽取型号、版本、故障码、命令、有效状态
  -> 按手册 / FAQ / 故障案例分段
  -> 版本化 Chunk Store
      ├─ Dense Index
      ├─ Sparse / BM25 Index
      └─ Exact Fields

User Query
  -> 提取型号、故障码、告警与意图
  -> ACL / 产品 / 版本过滤
  -> Dense + Sparse + Exact 召回
  -> 合并、去重、融合、Rerank
  -> 冲突和新鲜度检查
  -> Context Pack
  -> 生成分步骤建议或拒答
  -> 逐项引用来源
```

## 统一文档表示

```json
{
  "source_id": "manual-001",
  "source_version": "2.3",
  "chunk_id": "manual-001#3.2#01",
  "title_path": ["维护手册", "告警处理", "风扇告警"],
  "content": "...",
  "location": {"page": 42, "section": "3.2"},
  "metadata": {
    "product_models": ["S5735"],
    "fault_codes": ["ALM-12003"],
    "active": true,
    "valid_from": "...",
    "valid_to": null
  }
}
```

示例值用于说明 Schema。真实系统还需定义访问控制、文档所有者、解析置信度和删除策略。

## 分段策略

原方案提出按文档类型分段：

- 故障案例：尽量保留“现象—原因—检查—处理—验证”；
- 手册：沿标题层级和完整过程切分；
- FAQ：保持问题与回答成对；
- 命令与表格：避免从字段说明中间切断。

“单个 Chunk 为 800–1000 Token”仅是原方案候选值。是否合适要通过不同长度、重叠、父子 Chunk 和结构化切分的消融实验判断。

## Query 处理

示例 Query：

```text
S5735 出现 ALM-12003 风扇告警怎么处理？
```

解析结果可以包含：

```json
{
  "original_query": "S5735 出现 ALM-12003 风扇告警怎么处理？",
  "product_model": "S5735",
  "fault_codes": ["ALM-12003"],
  "symptom": "风扇告警",
  "intent": "troubleshoot"
}
```

Query Rewrite 可以加入标准术语，但必须保留原始 Query 和精确实体。正则或词典结果也需处理大小写、连字符、别名和误识别。

## 检索与重排

系统使用三类信号：

1. Dense 召回自然语言同义表达。
2. BM25 匹配术语、命令和稀有词。
3. `keyword` 或结构化字段精确匹配型号、故障码和版本。

候选合并后可比较加权融合与 RRF，再由 Reranker 对较小候选集精排。任何融合之前都应先应用访问权限和必要的产品/版本过滤。

详细机制见[混合检索与重排](../01-concepts/02-hybrid-retrieval-and-reranking.md)。

## 生成与引用

输出建议分为：

- 已由资料直接支持的事实；
- 有明确前置条件的操作步骤；
- 需要人工确认或高风险批准的动作；
- 资料不足、冲突或版本不明时的拒答/升级；
- 每个关键结论对应的 `source_id + version + location`。

RAG 负责提供可更新事实和来源；输出格式是否通过 SFT 或 Prompt 约束属于另一层设计。DPO、SFT 和 RAG 不是可以互换的组件。

## 需要验证的 Badcase

| 风险 | 测试样例 | 预期处理 |
| --- | --- | --- |
| 相似故障码混淆 | `ALM-12003` vs `ALM-12008` | 精确字段命中，错误码作为硬负例 |
| 口语与术语不一致 | “风扇灯红了” vs `FAN_FAIL` | Dense/Sparse 补充召回 |
| Query Rewrite 丢实体 | 改写后删除型号或编码 | 回退原始 Query，触发完整性检查 |
| 旧文档干扰 | 同一型号多个版本 | 按有效期和版本过滤，冲突显式展示 |
| 跨文档条件缺失 | 步骤依赖另一份安全手册 | Parent/linked retrieval 补充前置条件 |
| 无证据仍回答 | 语料中不存在该故障码 | 拒答并建议升级人工 |
| 越权知识泄露 | 用户无权访问内部手册 | 检索前 ACL 过滤并记录审计 |

## 评测计划

### Retrieval

- 建立真实 Query—Evidence 标注集；
- 按编码类、自然语言类、版本类和歧义类切片；
- 比较 Dense、Sparse/Exact、Union、Fusion 和 Rerank；
- 记录 Recall@k、MRR/nDCG、硬负例和延迟。

### Generation

- 主张是否被引用直接支持；
- 步骤、顺序和前置条件是否完整；
- 产品与版本是否适用；
- 无证据和冲突时是否正确拒答；
- 引用是否能回到原始页码或章节。

### System

- 多 Trial 端到端任务成功；
- 解析、检索、重排和生成分段延迟；
- Token、调用数和单次成功成本；
- 索引更新、删除和版本切换；
- 权限、注入和数据泄露测试。

## 当前可以与不可以得出的结论

可以说：该设计针对运维知识同时需要语义召回和精确标识符匹配，提出了多通道检索、版本化 Metadata、Rerank 和引用链路。

不能说：某个 Embedding、32B 生成模型、固定 Chunk 长度或 `0.3/0.7` 权重已经优于其他方案，也不能说系统已经在真实运维任务中稳定运行。
