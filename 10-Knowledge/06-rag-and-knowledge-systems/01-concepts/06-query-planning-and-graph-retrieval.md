# 查询规划与图检索：明确一次搜索究竟要找什么

> 状态：draft
> 资料核验：2026-09-06；编号约束与词法检索已运行，模型改写和 GraphRAG 未在本仓运行。

“ALM-12003 怎么处理？”与“过去半年不同告警有哪些共同原因？”需要的证据结构不同。前者可以定位一个完整处理步骤；后者可能需要遍历大量资料并统计归纳。查询规划的作用是选对搜索任务、保留原始约束，并在资料不足时决定下一次搜索。

## 改写解决表达差异，不能改掉问题

如果用户说“降温系统不畅”，手册只写“风道堵塞”，可以增加一个检索变体。原问题必须同时保留：扩展词是假设，原始实体、否定、产品和时间条件才是边界。

把 `ALM-12003 不允许重启时如何排查` 改成 `风扇故障重启步骤`，会同时丢失编号与否定。即使新 Query 的召回分数更高，任务已经变了。一个实用的保护办法是规则提取不可变槽位，让改写只调整描述部分。

```python
from rag_pipeline.ingest import identifiers
original = "ALM-12003 不允许重启时如何排查"
rewritten = "ALM-12003 读取日志 排查风扇异常"
assert set(identifiers(original)) <= set(identifiers(rewritten))
```

这条断言只保护编号，不理解“不允许”的语义。完整的改写契约还应保留结构化的禁止动作和时间范围；不能因为一个正则通过，就宣称改写没有失真。本仓对常见 `字母-数字` 编号采取硬匹配；空格分隔、设备别名、多编码比较问题需要更丰富的解析器。

## 分解用于不同证据，路由用于不同工具

| 操作 | 改变的对象 | 示例 | 错误风险 |
| --- | --- | --- | --- |
| 改写 | 查询表达 | 风道堵塞 → 通风受阻 | 扩展词把语义带偏 |
| 分解 | 所需证据 | 先查 A 适用版本，再查与 B 的差异 | 丢掉子问题间依赖 |
| 路由 | 搜索后端 | 编号走字段查询，依赖走关系表 | 错误路由让证据永远不可见 |
| 迭代检索 | 下一轮动作 | 初查发现缺少版本，补查发布记录 | 反复查相同内容耗尽预算 |

对于“DEMO-A v2 与 v3 的 ALM-12003 处理区别”，应分别检索两个明确版本再比较。只把问题拆成两条“风扇告警”会把版本丢掉。没有 v3 资料时，正确结果是指出缺口，不能拿 v2 内容充当两侧证据。

一个迭代检索循环需要可观察停止条件：所需事实已覆盖；授权范围内无新证据；连续查询只返回重复块；或预算已用完。停止时保留未解决项。它不是让模型无限“再搜索一次”。

## 图检索多做了什么

图用节点表示设备、组件、告警或文档，用带类型的边表示依赖、属于、引用等关系。查询“哪个组件故障可能影响这两个设备”可以沿依赖边寻找共同上游，再回到原文验证边是否可靠。

但“关系存在”也可能是抽取错误。每条边应附来源、版本和适用时间；两个同名实体不能只凭字符串相同就合并。方向也有意义：A 依赖 B 不等于 B 依赖 A。

[GraphRAG 原始论文](https://arxiv.org/abs/2404.16130)研究的是面向语料全局问题的查询式总结：从文档建立实体关系图，形成社区摘要，再按问题聚合相关摘要。它不能简单等同于“把向量库换成图数据库”，也不意味着任何局部问答都优于普通检索。本文只借其问题划分说明何时需要全局组织，没有复现论文性能。

## 怎么判断值得增加复杂度

先建立固定的一跳字段/关键词基线，再分切片比较。编号问题关注错误编号率；多跳问题关注每一跳证据是否齐全；全局问题关注主题覆盖、重复和不支持的概括。预算应包括查询、图抽取、摘要更新和生成成本，而不仅是最后一次调用。

可运行的[混合检索实验](../04-labs/01-hybrid-retrieval-evaluation.ipynb)保留跨语言表达失败，便于看到词法检索的边界。可以配置真实语义模型后重跑同一标注集，但不能用随机向量或哈希向量替代后把分数变化解释成语义提升。
