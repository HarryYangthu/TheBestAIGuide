# 切块与元数据：把检索单元做成能够独立理解的证据

> 状态：draft
> 资料核验：2026-09-06；段落切块与字符位置校验已在配套工程运行。

切块改变的是检索粒度。整本手册作为一个向量，容易把具体故障的信号摊薄；每句话一个向量，又可能把“仅限 v2”的条件与操作步骤分开。好的块要让检索器找得到，也让读者看得懂它为何适用。

## 一个真实会出错的边界

假设教学手册连续写了三行：

```text
适用范围：DEMO-A，软件 v2。
只有日志确认转速异常时，才检查供电连接。
不得直接重启；原因未确认时升级人工处理。
```

若第一块只包含最后一行，检索结果缺少适用版本；若只召回第二行，禁止动作又消失了。单纯增加重叠长度不能保证完整，因为条件可能离结论很远。先识别“适用范围 + 完整步骤”这个逻辑单元，比盲目调长度更直接。

| 策略 | 检索粒度 | 适用情况 | 必须付出的代价 |
| --- | --- | --- | --- |
| 定长窗口 | 固定字符或 token | 结构很弱、快速建立基线 | 可能切断表格、代码、条件 |
| 段落/标题切块 | 小节或段落 | 结构清楚的手册 | 标题很短、段落很长时要另定规则 |
| 父子块 | 子块召回、父块回读 | 小块易搜但缺上下文 | 回读增大窗口，父块仍需权限与版本检查 |
| 问答对/步骤组 | 一次完整知识操作 | FAQ、故障流程 | 需要可靠识别结构，不应模型猜完就直接入库 |

## 长度和重叠怎样算

对于长度为 \(L\) 的线性文本，块长 \(C\)，相邻重叠 \(O\)，要求 \(0\le O<C\)。若 \(L>C\)，覆盖文本所需窗口数为：

\[
N=1+\left\lceil\frac{L-C}{C-O}\right\rceil.
\]

例如 \(L=1000,C=300,O=50\)，得到 4 块；起点为 0、250、500、750，最后一块只有 250 个字符，总存储 1150 个字符。重叠增加了 150 个重复字符，也增加重复召回的机会。这些数字用于理解成本，不代表推荐长度。

注意这里是字符，不是 token。实际 embedding 模型的限制要用对应 tokenizer 计算，不能把“300 字符”写成“300 token”。尤其中文、代码和英文的 token 密度不同。

## 为什么位置比一个随机 ID 更有用

块至少应带：来源 ID、来源版本、租户、产品/适用范围、原文起止位置、内容哈希，以及长段落被强制截断的标记。引用应回到该版本原文，不能让同一个 ID 今天表示旧步骤、明天表示新步骤。

本仓块 ID 采用 `doc_id@version:start-end:hash`。`start/end` 是 Python 字符串索引，满足：

```python
assert original_text[chunk.start:chunk.end] == chunk.text
```

这是一条比“看起来没问题”更可检验的不变量。完整实现：[chunking.py](../05-code/rag-pipeline-python/src/rag_pipeline/chunking.py)。它按空行识别段落，过长段落按字符切分并设置 `split=True`；它不是完整 Markdown AST 解析器，不能保证围栏代码与复杂表格不被切断。使用文档解析器时，应先将这些结构识别为不可拆单元，再复用偏移与版本规则。

## 父子块如何接回代码

一种实现方式是让短块保存 `parent_id`。搜索只用短块表示，返回后从同一租户、同一文档版本取得父块，去重后装入上下文。这里的顺序很重要：父块回读也是一次数据访问，不能因为子块获准读取就假定整份父文档都获准。

检索评测可用子块 ID 判断定位能力，回答评测用完整证据组判断条件是否齐全。若把两者混成同一个 Recall，就会出现“命中了某一句，所以算完成”的虚高分。本仓实验按文档 ID 去重计算检索指标；跨块条件完整性尚未作为模型任务测试，不能把实验分数当作这项能力。

## 用标注决定参数

先固定几十条有代表性的查询：故障码、口语现象、跨段条件、表格参数、无答案。每条标出最小充分证据和不应命中的旧版本/相似编号。然后只改变切块策略，比较召回、前列噪声、实际入窗 token 和完整回答。

评测集合必须固定原文版本；否则切块参数没变、手册改了，结果差异也无法归因。将查询集按文档族划分开发和测试，避免同一手册的近重复问题两边都有。
