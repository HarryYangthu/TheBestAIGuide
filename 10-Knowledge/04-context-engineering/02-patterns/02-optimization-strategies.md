# 上下文优化策略

> 状态：draft
> 原则：优化目标是任务质量与可靠性，不是单独追求更少 Token。

## 策略全景

| 策略 | 解决的问题 | 主要代价或风险 |
| --- | --- | --- |
| Select | 候选信息太多 | 漏掉必要信息 |
| Retrieve | 信息不在当前窗口 | 召回错误、来源过期 |
| Reorder | 关键信息位置不佳 | 规则过度依赖特定模型行为 |
| Compress | 信息必要但体积过大 | 摘要失真、细节丢失 |
| Isolate | 子任务互相干扰 | 路由、交接和状态同步成本 |
| Offload | 中间状态不必常驻窗口 | 外部状态不一致、读取失败 |
| Cache | 稳定前缀重复计算 | 旧策略或旧工具定义未失效 |
| Refresh | 事实会随时间变化 | 查询成本、更新竞态 |

## Select：只保留当前决策需要的信息

选择通常比压缩优先。先删除无关、重复、过期和错误作用域的信息，再处理仍然过长的必要内容。

可组合的信号包括：

- 与当前目标和步骤的相关性；
- 来源权威性与验证状态；
- 时间与版本匹配；
- 对已有内容的新增覆盖；
- 敏感度与访问权限；
- 单位 Token 的预期价值。

避免使用单一相似度阈值承担所有判断。

## Retrieve：按需取得证据

检索不仅是向量搜索，还可以是：

- 结构化数据库查询；
- 关键词和精确字段匹配；
- 图关系或依赖查询；
- 文件系统与代码符号搜索；
- 工具目录搜索；
- 长期记忆读取。

检索输出应带来源、版本、时间、分数含义和可引用位置。RAG 的详细流程见 [RAG 与知识系统](../../06-rag-and-knowledge-systems/README.md)。

## Reorder：根据职责组织输入

一种常见组织方式是：

1. 系统策略与安全边界；
2. 当前目标、约束和验收条件；
3. 当前工作状态；
4. 与本轮决策直接相关的证据；
5. 可用工具与输出契约；
6. 最近观察和明确的下一步请求。

具体顺序应通过目标模型和任务集验证。不要把“放在开头或结尾”写成跨模型的固定规律。

## Compress：有损但可追溯地减少体积

压缩层次从低风险到高风险大致为：

1. 删除完全重复内容；
2. 结构化解析，移除展示噪声；
3. 抽取与当前问题相关的字段或句段；
4. 按事实、决策、证据和待办生成结构化摘要；
5. 对多轮历史做递归摘要。

每个有损结果都应记录原始来源、摘要方法、时间和截断状态。高风险任务应允许模型或人工回读原文。

## Isolate：为子任务建立独立工作集

适用于：

- 子任务需要不同工具和权限；
- 大量细节只对一个专门角色有用；
- 多个子任务可以并行；
- 需要限制某一来源的污染范围。

不适用于：

- 任务很小，交接成本高于上下文节省；
- 子任务边界不清，信息需要频繁共享；
- 没有明确的输入输出契约；
- 无法对路由和合并结果做评测。

隔离可以通过函数、工作流节点、独立进程、沙箱或子 Agent 实现，不必默认使用多 Agent。

## Offload：把工作状态移到外部介质

适合卸载的内容包括：

- 计划、待办和决策日志；
- 大型工具输出；
- 中间代码和数据文件；
- 已完成步骤的证据；
- 可按标识重新读取的原始文档。

外部状态需要原子写入、版本、并发控制和读取失败处理。文件存在不等于内容有效，模型说“已写入”也不等于写入真的发生。

## Cache：复用稳定前缀

缓存适合稳定系统策略、工具定义和固定参考材料。设计时同时考虑：

- 缓存键包含模型、策略和工具版本；
- 哪些变化必须使缓存失效；
- 供应商 Token 统计口径；
- 命中率之外的任务质量；
- 敏感数据是否允许进入共享缓存。

## 策略选择顺序

```text
信息是否真的需要？
  ├─ 否：Select 删除
  └─ 是：当前是否已有？
       ├─ 否：Retrieve / Refresh
       └─ 是：是否过长？
            ├─ 否：Reorder / Pack
            └─ 是：能否外部回读？
                 ├─ 是：Offload + 指针
                 └─ 否：Compress + 来源

子任务之间是否互相干扰？
  ├─ 是：考虑 Isolate
  └─ 否：保持单一工作流
```

## 验证要求

每次优化至少对比：

- 任务成功与硬约束通过率；
- 多次运行的稳定性；
- 关键证据是否被选中和正确使用；
- 输入、输出和缓存 Token；
- 延迟、工具调用次数和实际成本；
- 新增失败类型。

单独报告“节省了多少 Token”不足以证明优化有效。
