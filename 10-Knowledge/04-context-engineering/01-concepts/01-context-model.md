# 上下文模型：组成、边界与生命周期

> 状态：draft
> 前置：[Context Engineering 总览](00-overview.md)

## 上下文由什么组成

一次模型调用的上下文通常包含以下信息层：

| 信息层 | 示例 | 主要风险 |
| --- | --- | --- |
| 系统策略 | 角色、禁止事项、权限边界 | 被低优先级内容覆盖或稀释 |
| 当前请求 | 用户目标、约束、验收条件 | 歧义、隐含条件、目标漂移 |
| 工作状态 | 计划、已完成步骤、待决策项 | 过期、重复、状态不一致 |
| 对话历史 | 先前消息、确认和修正 | 长度膨胀、旧意图干扰 |
| 检索证据 | 文档片段、数据库记录、网页 | 来源不可信、版本过期、召回错误 |
| 工具定义 | 名称、描述、输入输出 Schema | 工具过多、描述重叠、权限不清 |
| 工具结果 | API、文件、命令或传感器输出 | 体积过大、错误未标记、敏感数据 |
| 环境约束 | 时间、分支、沙箱、可用资源 | 环境变化后仍沿用旧信息 |
| 输出契约 | JSON Schema、引用要求、停止条件 | 与任务目标或工具协议冲突 |

上下文不等于“消息数组”。文件、数据库状态、工具目录和外部记忆即使没有直接放入消息，也会通过选择与读取影响模型决策。

## 三个必须分开的维度

### 来源与信任

系统策略、用户输入、网页文本和工具返回的信任等级不同。外部文档中的命令式文字仍然是数据，不能自动升级为系统指令。

### 优先级与相关性

高优先级信息不一定与当前子任务相关；高度相关的信息也不一定可信。构建器应分别记录这两个维度，而不是用一个“score”混在一起。

### 原文与派生物

摘要、实体抽取和结构化转换都可能丢失信息。派生内容应带有：

- 原始来源标识；
- 转换方式和版本；
- 生成时间；
- 可回读的原文位置；
- 不确定性或截断标记。

## 生命周期

```text
候选信息
  -> 收集：从请求、状态、检索、工具和环境获取
  -> 分类：标注来源、信任、时效、敏感度和生命周期
  -> 选择：按任务相关性和约束筛选
  -> 转换：去重、结构化、摘要、引用化
  -> 排序：把约束、证据和当前工作状态放到可用位置
  -> 打包：满足模型接口和 Token 预算
  -> 校验：冲突、缺失、注入、泄露、格式检查
  -> 使用：执行模型调用
  -> 反馈：把结果和环境变化写回状态或记忆
  -> 失效：过期、替换、归档或删除
```

## 上下文质量维度

一个片段是否值得进入窗口，至少要看：

- **Relevance**：是否影响当前决策。
- **Authority**：来源是否有权定义该事实或约束。
- **Freshness**：是否仍适用于当前时间和环境。
- **Specificity**：是否比泛化描述更直接。
- **Consistency**：是否与其他事实冲突。
- **Utility per token**：占用预算是否带来足够增益。
- **Safety**：是否包含敏感数据、恶意指令或越权信息。

这些维度不能总被压缩为固定权重。权限约束通常是硬门禁；相关性和 Token 效率更适合做排序信号。

## 冲突处理

当上下文出现冲突时，不应静默选一个版本。建议流程：

1. 先按权限和来源判断哪一方有资格定义该信息。
2. 再按版本、时间和适用范围判断是否只是条件不同。
3. 能通过工具或事实源验证时，优先验证。
4. 无法消解时，在状态中显式记录冲突和不确定性。
5. 冲突会实质改变结果时，向用户或上游系统请求决策。

## 最小不变量

无论使用何种框架，Context Builder 都应维持这些不变量：

- 不丢失任务目标、硬约束和停止条件。
- 不把不可信内容提升为指令。
- 不把失败的工具结果写成成功事实。
- 不隐藏关键来源、版本或截断信息。
- 不因压缩而删除仍未完成的承诺与待办。
- 不把跨用户、跨租户或跨任务数据混入当前上下文。

## 常见误解

- **窗口越大越好**：容量增加不等于注意力分配和信息质量提高。
- **摘要后可以删除原文**：摘要可能需要回溯，尤其是法律、科研、运维和代码任务。
- **Memory 会自动改善 Agent**：错误或过期记忆会稳定地产生错误。
- **多 Agent 天然能隔离上下文**：如果共享状态和交接协议不清，冲突只会移动到系统层。
