# 从失败评分到改进：先找到故障所在层

> 状态：draft · 来源核验：2026-09-06 · 教学示例均为本库原创，非生产成绩。

一个任务失败了，先调 Prompt、加记忆还是训练模型？分数本身不能给出答案。先把任务轨迹对齐到“读输入—选动作—执行—验收”，找到最早可证实的错误，再选择改动位置。

## 用可观察的错误决定动作

| 观察到的证据 | 更可能的故障 | 优先改动 | 用什么验证 |
|---|---|---|---|
| 正确文档从未被检索到 | 数据/检索 | 摄取、切块、召回 | Recall@k 与权限过滤 |
| 文档已提供，关键约束仍被漏掉 | 上下文组织/决策 | 放置约束、压缩保留规则 | 长短输入配对任务 |
| 工具名对、参数类型错 | 输出契约 | Schema、约束生成、工具 SFT | 合法调用率及任务成功 |
| 合法调用因服务超时失败 | Runtime/服务 | 超时、状态查询、幂等恢复 | 故障注入 |
| 可执行方案中反复选较差方案 | 策略偏好 | 规则、偏好数据或 RL | 同预算独立任务集 |
| 正常得分高，但会伪造完成 | 评分器 | 独立验证、奖励反例 | 奖励投机测试集 |

这些是定位假设，不是看见症状就自动得出的根因。比如“漏约束”也可能是约束被截断；先看实际模型输入再动 Prompt。

## 一个具体迭代

教学任务要求读取采购规则并填写本地表单。失败轨迹中模型选对了金额，浏览器提交按钮点击超时，随后重复提交。若直接把这条记录标成“推理失败”去训练，就把外部状态不确定性错误归因给模型。应先让执行器在超时后查询完成标记，保留动作 ID，再决定是否重试。[浏览器案例](../../13-application-engineering/03-cases/browser-agents/README.md)有实际实现。

改动后固定任务、环境和预算，用旧版与新版分别执行。配对比较同一道题的结果，记录“旧失败新成功”和“旧成功新失败”。后者是回归，不能被总体平均分掩盖。任务集只要用于调参，就已成为开发集；最终保留集需要新任务且不可反复窥看。

## 什么情况下再训练

至少同时满足：错误反复出现、工具和数据问题已排除、存在可验证的正确轨迹、预期使用量足以摊薄训练维护成本。先做一小批高质量样本验证方向，保留来源、去重组和许可。上线时版本应关联模型、Prompt、工具、检索和验证器，不能只记录“模型 v2”。

```python
old = {"a": False, "b": True, "c": True}
new = {"a": True, "b": False, "c": True}
fixed = [k for k in old if not old[k] and new[k]]
regressed = [k for k in old if old[k] and not new[k]]
assert fixed == ["a"] and regressed == ["b"]
```

这个例子净成功数没变，却发生一次修复和一次回归。它说明为什么改进记录必须保留逐题结果。完整的训练前检查见[轨迹数据](../01-concepts/01-trajectory-data.md)，数值验证见[Notebook](../04-labs/01-trajectories-and-rewards.ipynb)。方法出处和适用边界见[来源](../references.md)；本节故障定位表是工程归纳，不是某篇论文证明的定律。
