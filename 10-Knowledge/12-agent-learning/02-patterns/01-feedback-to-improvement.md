# 从失败评分到改进：先找到故障所在层

> 状态：draft。Pine SDK 与分数表是教学例子；末尾的查询实验对应仓库实际代码。这里讲改进流程，不声称系统已经能自主训练或自动上线。

Agent 写错了 Pine SDK 的超时值，你给提示词加了一句“请认真核对版本”。再跑一次答对了，于是决定保留这句提示。两天后另一道题仍然读了废弃文档。第一次成功究竟来自修改，还是模型这次刚好选对了？只有一条成功记录，回答不了这个问题。

所谓自进化，至少要把“发现失败、提出修改、验证修改、保留或撤销”接起来。被修改的可以是提示词、工具、Skill 或执行策略，未必涉及模型训练。**它的难点不是让模型生成新提示词，而是有证据决定新版本是否值得采用。**

## 用可观察的错误决定动作

从最终结果回看 Trace。假设清单写了 5 秒，工具记录显示它读取 `preview.md`；再往前看，工具描述只说“读取文档”，文件列表没有告诉它哪个版本已经废弃。此时有两个候选原因：提示词未强调正式版，或工具提供的资料缺少版本信息。先把它们写成待验证假设，不能因为模型答错就认定要训练。

| 证据在哪里断掉 | 先检查什么 | 一次可以尝试的修改 |
| --- | --- | --- |
| 正式文档从未进检索结果 | 数据与检索范围 | 修复索引或查询过滤 |
| 检索到了，装配后不见了 | 上下文选择与裁剪 | 保留版本标记和关联原文 |
| 信息完整，却生成错误字段 | 决策与输出约束 | 修改提示词或结构化检查 |
| 参数正确，调用提交后超时 | 外部动作与恢复 | 查询动作状态，保持幂等身份 |
| 结果实际错误却拿到高分 | 验收规则 | 补独立检查和错误反例 |

这些是排查方向，不是自动判定表。同一个“漏引用”可能发生在检索、上下文或生成阶段，必须查看当时实际输入。运行中的 Evaluator 与离线评测的分工，见[评测对象与系统模型](../../10-evaluation-observability/01-concepts/01-evaluation-model.md)。

## 一个具体迭代

我们先限定一个假设：“工具返回的文档身份不清楚，导致误用预览稿。”候选修改只做一件事：让文件列表同时返回版本和 `draft / released / deprecated` 状态，其他模型、提示词、预算和验收规则保持不变。这样，观察到差异时才较容易判断是不是该修改带来的。

先把触发问题的资料保存为开发案例：输入文档、原结果、工具返回值、验收失败项、相关版本都留下。修复后重新运行，确认模型获得了新字段，并检查清单是否真的改成正式版。只看“本次通过”，还不足以知道代码改动是否被实际执行。

再拿一组开发题测试，包括文件状态明确、名称含糊、只有旧版资料等情况。如果工具已经修好，却仍错把旧版当新版，就继续分析；不要顺手同时换模型、加记忆、延长预算，否则无法解释哪个变化有效。

## 提示词、工具、Skills 和策略分别怎么改

如果问题确实是遗漏一条任务规则，可以修改提示词；如果工具返回的字段容易误解，应该修改工具契约与说明。某类任务已经形成可靠步骤，才适合把“确认版本 → 比较三项字段 → 补齐双方引用”整理为 Skill，并附验证方法。

策略改动改变的是系统什么时候采取哪种行动，比如只有引用检查失败时才补查一次，而不是每道题都多检索三轮。它可能提高成功率，也可能增加耗时和费用，因此需要在相同预算或明确标出的预算差异下比较。

这些修改都可以由人写，也可以由另一个 Agent 提议；是否自动产生候选，不改变后面的验收要求。未经验证的“经验”若直接写入长期 Memory，会把一次偶然判断带到未来所有任务中。

## 开发集与保留集为什么必须分开

反复用来观察错误、修改工具的那些题，就是开发集。即使最初叫“测试集”，一旦你根据它调参，它已经参与开发。候选可能只是记住了 `preview.md` 这个名字，所以还需要从未用来调过方案的保留题，例如文件名变了、正式版变成 v3、干扰资料来自另一目录。

任务应按来源或相近问题分组，避免同一文档的轻微改写一份进开发集、一份进保留集。最终评测前固定任务 ID、数据版本、评分规则和采用条件。保留结果一旦被拿来继续改方案，这组题就不再是未见证据，应进入开发或回归材料，并补充新的保留题。

采用条件也要提前定。比如关键权限题不能失败，原有成功题不得退化，额外调用次数不能超过设定预算。这是项目选择的门槛，不是所有 Agent 都通用的常数。

## 不要只看总分，逐题数修复与退化

下面是**教学演算，不是实测指标**。固定 4 道题，旧版、新版各运行一次：

| 任务 | 旧版 | 新版 | 应记录什么 |
| --- | --- | --- | --- |
| 正式版与预览稿混放 | 失败 | 成功 | 修复 1 题 |
| 用户明确要求查旧版 | 成功 | 失败 | 退化 1 题 |
| 正常升级清单 | 成功 | 成功 | 保持 |
| 资料本身缺失 | 失败 | 失败 | 尚未解决 |

两版都为 `2/4=50%`。平均分没变，却发生了重要变化：新规则可能错误地把“旧版”一律过滤掉。下面代码可以直接运行，保留这种差异，而不是只输出一个总分。

```python
old = {"preview": False, "requested-old": True,
       "normal": True, "missing": False}
new = {"preview": True, "requested-old": False,
       "normal": True, "missing": False}
assert old.keys() == new.keys()
fixed = [key for key in old if not old[key] and new[key]]
regressed = [key for key in old if old[key] and not new[key]]
print("fixed:", fixed)
print("regressed:", regressed)
print("old/new:", sum(old.values()) / len(old), sum(new.values()) / len(new))
accept = not regressed and sum(new.values()) > sum(old.values())
print("accept:", accept)
```

输出修复 `preview`、退化 `requested-old`、两版均 0.5，最后是 `False`。这是一个简单教学采用规则。真实模型存在波动时，应保留每道题的多次 Trial、配置与误差分析；不能把一次成败当作稳定能力变化。

即使总体从 70% 涨到 80%，新增的越权或重复提交问题也可能让候选不值得采用。成功率、成本、耗时与关键失败分开看，才能说明“改善了什么，付出了什么”。

## 采用之后，还需要能撤销

候选通过验收后，保存一组可恢复的版本：代码提交、模型、提示词、工具、Skill、上下文构造器和评测配置，并关联本次实验结果。只写“升级为 v2”，下次失败时很难知道要退回哪一部分。

上线可以先限制任务范围，观察真实失败与费用。如果触发预设退回条件，切回旧配置并保留失败样本。这种回滚改变后续任务的执行版本，不会自动撤销已经发出的邮件、写入的记录或其他外部效果；那些需要单独恢复或补偿。

## 运行内 Reflection 与跨任务改进有什么不同

当前任务发现缺一条引用，Agent 再读文件并改答案，是运行内的反思与修正。任务结束后，下一次仍使用原提示词、原工具和原策略。跨任务改进则把经过验证的修改保存成新版本，让以后任务也受益。

两者可以相接：Reflection 的失败记录可成为开发材料，但不能每次反思都直接覆盖共享提示词。当前任务的临时补救可能只适合这一题。长期更新需要独立评测和回滚能力，具体作用对象见[轨迹数据](../01-concepts/01-trajectory-data.md)。

## 什么情况下再训练

当错误反复出现、数据与工具问题已排除、存在可验证的正确轨迹，并且调用规模值得承担训练维护成本时，再考虑 SFT、偏好优化等训练路线。训练要有来源、去重、许可与划分记录，不能把保留题答案混进样本。

例如浏览器已提交成功、客户端超时后重复点按钮，优先修复状态核对与幂等处理。把它标成“模型推理失败”做训练，不会让外部接口突然具备可靠恢复能力。[浏览器案例](../../13-application-engineering/03-cases/browser-agents/README.md)可以用于观察这类差别。

## 运行一个已有的“失败、修改、比较”实验

从仓库根目录执行：

```bash
cd 10-Knowledge/10-evaluation-observability/05-code/eval-harness-python
PYTHONPATH=src python -m eval_harness.cli
```

PowerShell 先设置 `$env:PYTHONPATH="src"`。现有[查询案例](../../10-evaluation-observability/03-cases/01-from-task-dataset-to-regression.md)的基线遗漏租户与版本检查，候选补上过滤；4 道题各跑 2 次，参考结果从 `2/8` 到 `8/8`。打开 `reports/comparison.json`，应看到 `passed=true`、退化题列表为空，改善题为 `wrong-tenant`、`old-version`、`missing-version`。逐题证据在两版的 `trials.jsonl`。

这个实验展示的是确定性函数的定位与配对验收。候选函数已经写在源码里，没有自动生成候选、划分保留集或自动上线，所以不能据此宣称实现了完整自进化。它提供可复用的评分接口；完整流程还需补齐本篇前述的版本与发布环节。

## 检查自己是否理解

**练习一：** 连续查看保留集结果五次，并据此调提示词，第六次高分还能作为未见效果吗？参考解释：不能。这组题已经参与优化；保留其回归价值，另外准备未用于调参的任务验证泛化。

**练习二：** 新版成功题更多，但新增一次重复提交，是否该上线？参考解释：先查预先约定的关键失败门槛与副作用记录。若重复提交被定义为不可接受，就应拒绝候选或先修复；多答对几题不能抵消执行错误。

相关数值练习见[轨迹与奖励 Notebook](../04-labs/01-trajectories-and-rewards.ipynb)，方法出处与适用范围见[本域来源](../references.md)。返回 [Agent 核心组件总览](../../03-agent-core/01-concepts/04-core-components.md)时，把自进化理解为“用经过验证的修改改善后续任务”的过程，就不容易把它与当前轮反思或模型训练混为一谈。
