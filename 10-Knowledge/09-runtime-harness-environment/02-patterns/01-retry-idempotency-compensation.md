# 重试、幂等与补偿：重复尝试不应重复改变世界

> 状态：draft；来源核验：2026-09-06；本地恢复与幂等实验已实跑，生产能力不在验证范围内。


请求失败后直接 `except: retry()` 看似让程序更稳定，却可能把一次扣款变成两次，把一次文件发布变成多个版本。正确处理先回答：失败发生在哪里，原动作有没有可能已经生效，重复执行是否安全。

## 按错误性质选择动作

| 观察 | 可以直接重试吗 | 正确处理 |
|---|---|---|
| 参数格式错误 | 不可以 | 修正输入或结束 |
| 缺权限、审批不匹配 | 不可以 | 获得合法授权，不能循环撞接口 |
| 请求尚未发送就失败 | 通常可以 | 保留同一步骤身份重试 |
| 下游限流、暂时不可用 | 视接口契约 | 有界退避，遵守服务端建议 |
| 发送后超时，结果未知 | 不能盲目重发 | 同幂等键重试或查询结果 |
| 业务已提交但后续步骤失败 | 不是重试前一步 | 根据业务语义做补偿 |

## 幂等到底保证什么

从状态变换看，幂等满足 \(f(f(s,a),a)=f(s,a)\)：在状态 \(s\) 上重复执行同一个逻辑动作 \(a\)，效果与一次相同。读取、设置某字段为固定值通常容易做到；“余额加 10”本身不幂等，因为执行两次会加 20。

本例为每个逻辑动作带唯一 key，账本先检查该 key 是否执行过。检查与业务效果写入同一事务。如果检查后再单独写入，两个并发请求都可能看到“未执行”，仍然会重复生效。

同 key 的不同参数必须拒绝。如果第一次是给 A 加 10，第二次变成给 B 加 100，返回第一次结果掩盖了调用方错误，执行第二次则违反去重意图。幂等键不是“忽略所有重复请求”的许可证。

## 退避如何减轻负载

第 \(k\) 次重试可使用上界 \(d_k=\min(d_{max},d_0 2^k)\)，实际等待在 \([0,d_k]\) 中均匀随机抽取，称为 full jitter。\(d_0\) 是初始退避，\(d_{max}\) 限制最大间隔。随机化让大量客户端不在完全相同的时刻一起重试。

```python
# 策略示意；本地故障实验手动恢复，不真的等待外部服务。
delay = random.uniform(0, min(max_delay, base_delay * 2 ** retry_index))
if delay + estimated_attempt_time > remaining_deadline:
    raise TimeoutError("no retry budget left")
```

次数预算和总期限也要同时限制。重试三次可能意味着总共四次尝试，应在配置中写清“max_attempts 包含首次”。

## 补偿为什么不叫回滚

回滚撤销同一事务内尚未提交的改变；补偿是提交之后再执行一个新的业务动作。例如原扣款已被外部系统确认，后续订单失败，系统再发退款。扣款记录没有消失，退款也可能失败、被重试或需要对账。

本例 `compensate` 创建一条独立退款记录，并按原操作 key 去重。如果在退款后、补偿 Checkpoint 前崩溃，再次补偿不会退款两次。状态为 pending 时先拒绝补偿，要求执行恢复查询原效果；否则可能不知道有没有可补偿的动作。

不是所有副作用都能补偿。已经读到的秘密不能“退回”，已经被收件人看到的消息无法真正撤销，外部物理动作也可能不可逆。选择补偿动作应由业务定义，不由模型临时发明。

## 怎样证明这个设计确实有效

[Notebook](../04-labs/01-recovery-and-idempotency.ipynb)在调用前、调用后、Checkpoint 后注入故障，再关闭并重开数据库。每种逻辑动作最终恰好一条扣款记录；多次 replay 不增加记录；退款后崩溃再补偿，退款记录仍只有一条。检查的是实际账本内容，不是日志里打印的“成功”。
