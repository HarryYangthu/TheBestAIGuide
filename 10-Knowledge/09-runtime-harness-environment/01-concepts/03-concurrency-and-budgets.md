# 并发与预算：让任务数量、速度和积压都有上界

> 状态：draft；来源核验：2026-09-06；本地恢复与幂等实验已实跑，生产能力不在验证范围内。


同时启动 100 个任务不等于同时完成 100 个任务。如果下游每秒只能处理 5 个，其余任务会排队、超时，再触发更多重试。负载增加时越重试越拥堵，通常说明系统缺少背压：下游处理不了时，上游必须放慢或拒绝继续接收。

## 五个限制管的是不同的事

| 机制 | 限制什么 | 例子 |
|---|---|---|
| 并发上限 | 此刻有多少请求正在执行 | 同时最多 6 个模型请求 |
| 速率限制 | 一个时间窗内允许多少请求 | 每秒最多 5 次 |
| 队列上限 | 等待处理的任务数 | 最多积压 50 项，再多返回繁忙 |
| 总预算 | 一次 Run 总共能花多少 | 最多 20 次调用或 100k Token |
| 截止时间 | 任务最晚什么时候结束 | 排队加执行合计 30 秒 |

信号量能限制并发，不能限制每秒调用量。10 个并发请求若每个只需 10 ms，一秒仍可能发出约 1000 次。速率限制可以用令牌桶：以固定速度补充令牌，每发一次请求消耗一个；桶容量限制突发量。

## 从队列长度判断是不是可持续

在稳定系统中，Little 定律写成 \(L=\lambda W\)：\(L\) 是平均系统内任务数，\(\lambda\) 是平均到达率，\(W\) 是平均停留时间。单位必须一致。例如每秒进入 4 个任务，平均从入队到完成要 3 秒，则平均系统内约 12 个任务。

这不是容量保证：如果到达率长期大于处理率，系统不稳定，积压持续增长，不能用一个有限的平均值替代扩容或拒绝策略。规划容量时还应看峰值、长尾任务和重试流量。

## 排队时间也会花掉用户的期限

本例把 `asyncio.wait_for` 放在取得信号量之前，因此期限覆盖排队和执行。如果把它仅包在 Worker 函数外、却先无限等待队列名额，所谓“1 秒超时”可能先排队一分钟。

```python
async def perform(task):
    async with semaphore:
        return await worker(task)

result = await asyncio.wait_for(perform(task), timeout=task.timeout_s)
```

完整代码见[Supervisor](../../08-planning-workflow-multi-agent/05-code/multi-agent-runtime-python/src/multi_agent/supervisor.py)。它在任何委派前检查总任务数，并为每个任务记录 queued、started 和最终事件。`started - queued` 是排队时间，最终事件与 started 的差是执行及清理时间。trace 字段是本库自定义教学格式，不冒称稳定遥测标准。

## 取消不是撤销已发生的效果

取消的第一步是停止等待和后续任务；已经发出的外部动作需要查询或补偿。Python 协程取消会在可中断点抛出 `CancelledError`，Worker 应在 `finally` 中释放资源后继续传播。吞掉这个异常会让父任务以为已取消，子任务却继续运行。

`wait_for` 可能等待被取消任务完成清理，因此实际耗时可能超过名义 timeout。阻塞函数和不合作的远端任务不能靠协程取消强制终止。需要进程边界、远端取消协议或超时后的隔离清理，并记录结果是否仍未知。

设计上先给有限队列、有限并发、有限重试，再考虑自动扩缩容。让用户看到“排队中/执行中/取消处理中”，比让所有状态都显示一个转圈更便于判断。API 语义参考[Python 官方任务文档](https://docs.python.org/3/library/asyncio-task.html)；排队公式的原始来源见[来源索引](../references.md)。
