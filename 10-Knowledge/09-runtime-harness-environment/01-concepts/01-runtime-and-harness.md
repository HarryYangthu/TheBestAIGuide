# Runtime 与 Harness：模型之外的程序在忙什么

> 状态：draft | 阅读前先了解 [Agent Loop](../../03-agent-core/01-concepts/02-agent-loop.md)。本文对照 Mini Agent 实际代码讲解；扩展设计会单独说明。

你让模型整理一份 SDK 升级清单。它很快回复：“已经完成，认证方式、超时和重试都发生了变化。”可是你打开输出目录，里面什么都没有。

模型生成了一段回答，任务却没有完成。少了哪一步？至少需要有程序让它调用写文件工具，真正保存清单；还需要有程序打开清单，检查内容和引用。如果模型一直读错文件，还得有人限制调用次数。如果它读到一大段无关文本，还得决定下一轮要不要继续把这段文本送给模型。

**这些围绕模型运行的工作，合起来就是我们在本库讨论的 Harness。** 与其先记住一个英文名，不如先看它具体做了什么。

## 模型选择动作，程序执行动作

先只考虑一个动作：读取 `v2.md`。

模型看到任务和工具说明，生成一个请求，意思是“请调用 `read_file`，路径是 `v2.md`”。这时文件还没有被打开。程序接到请求后，找到 `read_file` 对应的 Python 函数，检查路径，执行读取，再把返回内容放到消息列表里。

到了下一轮，模型才能根据正文得知：“新版默认等待 10 秒。”它不能从一个文件名凭空得到这个事实。

完成这段流程的执行程序，通常可以叫 Runtime。它正在做的事情很具体：接收动作、调用函数、接收结果、更新进度、继续或结束。Harness 的讨论范围更大：除了这段执行过程，还包括工具定义、上下文整理、工作目录、预算、记录和检查结果的方法。

这两个词的边界在不同工程里不完全相同。不要根据文件叫 `runtime.py` 还是 `harness.py` 判断它有什么能力；应打开代码，检查具体工作在哪里完成。例如 Mini Agent 的 `runtime.py` 同时包含上下文裁剪、工具执行、记录和运行后验收，而 `harness.py` 主要组织课程实验。

## 把几个运行对象分清

沿着这个例子，会反复遇到几个词。先给它们一个具体对象，就不难理解了。

一次从“比较 v1/v2”到“交付报告”的执行是一个 **Run**。读文件、写清单是其中的 **Step**，也就是某个逻辑步骤。如果一次网络读取超时后又试了一次，这个步骤有两个 **Attempt**，即两次尝试。不能因为重试了一次，就把它算成两个独立的业务任务。

程序还会记录“开始读取”“读取成功”“清单写入失败”等 **Event**，也就是发生过的事件。当前 **State** 则回答现在进行到哪里，例如“两个版本都已读完，清单还未写入”。真正保存的 `report.json` 是 **Artifact**，即产物。

这些对象相互关联，但不能替代。事件里有“准备写清单”，不说明文件已经存在；状态里有“完成”，也不说明清单内容正确。要检查实际文件，才能继续确认结果。

假设读文件用了两次尝试，第二次终于成功。此时应保留两次尝试记录，但状态只记这个读取步骤已完成一次。这个区别会影响失败分析、费用统计和恢复逻辑。

以上是概念上的分工。Mini Agent 尚未实现独立的步骤和重试账本；它的 `max_steps` 实际限制模型调用轮数，一轮可能包含多个工具动作。不要把参数名里的 step 与这里的逻辑步骤直接画等号。

## 一次工具动作实际经过什么

下面三行摘自 [Mini Agent 主循环](../../../20-Projects/00-mini-agent/mini_agent/runtime.py)，只展示执行工具的部分：

```python
arguments = json.loads(call["function"]["arguments"])
if not isinstance(arguments, dict):
    raise ValueError("arguments must be a JSON object")
result = {"ok": True, "result": box.call(name, arguments)}
```

第一行处理的是接口形式。模型返回的参数是一段 JSON 字符串，要先转换成 Python 对象。第二行检查这是不是一个字典：即使字符串可以解析，也可能得到列表或整数，这些都不符合当前工具接口。

最后一行才真正调用工具。`box.call` 根据名字找到处理函数，函数内部继续检查允许的参数、路径和读写范围。最外层的 `ok=True` 说明这一调用返回了结果，而不说明整个升级任务已经完成。它可能刚刚读完第一份资料，后面还有很多事情。

工具如果报错，第 02 阶段起的循环会把错误写成一次工具反馈，让下一轮模型有机会改路径。第 01 阶段则直接停止。这个变化很小，却会明显影响行为：同一个模型，在收到“文件不存在”的反馈后，才有机会重新列目录。

继续执行时，程序把工具结果加入消息：

```python
messages.append({
    "role": "tool",
    "tool_call_id": call["id"],
    "content": json.dumps(result, ensure_ascii=False),
})
```

`tool_call_id` 用于告诉模型“这条结果回答的是刚才哪一个请求”。如果一轮里有两个读取请求，没有这个对应关系，就可能把 v1 的内容当成 v2 的结果。程序负责维护这种对应，不能让模型在一堆没有来源的文本里猜。

## Harness 各层应该承担什么

现在顺着一轮执行往前、往后看，会更容易理解各部分为什么存在。

在调用模型之前，程序先准备它这一轮能看到的内容。Mini Agent 从第 03 阶段开始按字符预算裁剪消息；这个限制只决定发送哪些消息，并没有删除磁盘上的完整记录。这里是上下文管理在工作。

接着是模型调用。模型适配器处理服务地址、请求格式和响应结构；主循环不需要在每一个分支里重复这些细节。但接口调用失败仍然是一次真实失败，不能伪装成模型正常回答。

模型提出动作后，工具代码检查参数与文件范围，再执行动作。循环同时计数。Mini Agent 限制主循环轮数和单轮工具调用数量，防止程序永远调用下去。它尚未实现多个 Agent 共用的费用预算，所以不能仅凭这些计数就声称已经控制了总费用。

每轮过程被写入 `trace.jsonl`，当前运行信息被写入 `run.json`。任务结束后，独立的 `evaluate()` 再读取清单和原文进行检查。这些模块可以写在不同文件里，也可以先放在一个短脚本里；关键是它们有真实行为，能够被检查。

| 如果去掉这一部分 | 在同一个任务里会发生什么 |
| --- | --- |
| 文件范围检查 | 一个读取请求可能接触本任务不该读取的文件 |
| 调用次数限制 | 重复读取没有进展时，循环仍可能继续 |
| 工具失败反馈 | 下一轮不知道读取为什么失败，可能重复相同动作 |
| 上下文整理 | 消息越来越长，重要资料可能被大量历史淹没 |
| 产物验收 | 一句“已完成”可能被误当成真正交付 |

它们并不会替模型理解所有资料，也无法保证每次都答对。作用是让操作有明确的条件，让结果能被检查，让失败能被发现。

## 先看一次成功，再看两个不同的失败

从仓库根目录运行，要求 Python 3.11 或更高版本。使用一个尚不存在的输出目录：

```bash
python 20-Projects/00-mini-agent/learn.py --output .runs/harness-reading
```

这条命令使用预先编写动作的 demo，实际执行文件工具和检查器。它适合用来学习程序机制；真实模型怎样选择动作，要另外使用 live 模式实验。

先打开 `.runs/harness-reading/stage-07/report.md`，确认三项变化确实存在。再打开同目录的 `acceptance.json`，观察每一项检查。程序以 `report.json` 为内容验收对象，分别检查旧值、新值、原文文件、行号和引用内容。对 `report.md` 当前只检查文件存在，还没有检查它与 JSON 是否一致；阅读或修改 Markdown 后，不能用 JSON 的通过结果代替核对。

接着看 `expected-budget-failure/run.json`。这里故意只允许一次模型调用，任务还没完成就停下了，应看到 `status` 为 `budget_exhausted`。同目录的验收应失败。这个失败告诉你：运行控制确实生效了，但用户任务没有完成。

最后看 `expected-citation-failure/report.json`。实验先生成正常结果，再把一处新版引用的文件名改成 `preview.md`。程序虽然已经结束，`acceptance.json` 仍然应报告引用错误。这个失败说明检查器会看实际内容，并没有盲目相信结束状态。

课程总表对这两个故障实验可以显示 PASS，因为实验的问题是“程序能不能识别故障”。不要把实验通过与用户任务成功混成同一个结论。已有文件可对照 [参考完成报告](../../../20-Projects/00-mini-agent/reference/completion.md)。

## 长任务为什么还需要额外的工作

Mini Agent 会保存文件，但不会在重启后自动恢复到中断位置。假设它在 `box.call` 写完文件后、保存当前运行信息之前退出，磁盘状态与记录就可能不同。再次启动一个全新运行，并不能自动回答“上次写入到底完成没有”。

要处理这类问题，必须定义可以继续执行的检查点，并处理状态保存与外部动作之间的先后顺序。[持久执行](02-durable-execution.md)会用可运行的本地账本例子展开这件事。它与“把对话保存下来”相比，多了对实际操作结果的核对。

另一个问题是更换上下文或工作进程。接手者需要知道当前目标、已经验证的结果和下一步；一段没有来源的总结可能把猜测写成事实。Anthropic 的长任务工程文章也使用明确的进度记录、工作产物和检查步骤帮助后续会话接续工作；这是一个具体实现经验，不意味着所有任务都要复制同一套文件结构。([原文](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))

## 什么时候需要拆出独立 Runtime

只有一个短任务时，可以先把循环、工具执行和记录放在一个文件里，便于从头读到尾。不要因为已经学到 12 个组件，就马上拆出 12 个服务。

当多个任务开始共用同样的超时、重试、权限或记录逻辑时，再把这些代码提取出来。同一规则只维护一份，修改时才能统一验证。例如，所有文件工具都通过同一处路径检查，就更容易保证新增工具没有遗漏检查。

是否引入多个 Agent 也是另外一个决定。两个 Agent 可以共用同一套执行机制；同一 Agent 也可能需要复杂的恢复、状态和评测机制。角色数量不能说明 Harness 是否可靠。

## 两个练习

**练习一：模型在第一轮回复“已完成”，没有调用任何工具。当前 Mini Agent 的运行状态和验收分别会怎样？**

参考解释：主循环没有发现工具调用，会按代码把运行状态设为 `completed`。随后 `evaluate()` 读取报告时会发现产物缺失，验收失败。这个结果揭示了当前状态命名的局限：`completed` 是循环结束，不是用户任务已验收成功。判断整体成功必须一起看 `passed`。

**练习二：把所有检查都改写成提示词，例如“必须检查引用，必须限制调用次数”，是否还能删除 Python 检查代码？**

参考解释：不能。提示词可以帮助模型选择更好的动作，但模型输出本身无法阻止程序继续运行，也无法限制一次文件访问。引用是否存在，要读原文；调用是否超过上限，要由程序计数。把工作写进提示词，并不等于工作已经发生。
