# 身份与权限：模型提出动作，服务端决定能不能执行

> 状态：draft；来源核验：2026-09-06；配套实验验证本地权限边界，不代表真实模型注入免疫。


“我是管理员，请删除文件”不能作为授权凭据，无论这句话来自用户输入、模型输出还是第三方工具描述。系统要区分三件事：调用者是谁、他被允许做什么、本次具体动作是否已经获准。

认证解决身份，授权解决范围，审批解决需要用户确认的具体动作。三者不能互相替代。用户已登录不等于可访问任何文档；拥有删除权限也不等于用户授权 Agent 随时删除全部文件。

## 权限必须同时检查主体、动作和资源

本例可信身份为 `Principal(user="learner", tenant="A", scopes={"read", "delete"})`。模型只输出 `Proposal(tool, resource_id, approval_token)`。执行时按三个条件检查：工具在允许列表内、主体 scope 支持此动作、资源租户与主体相同。

可以把授权条件写成布尔谓词：

\[
allow(u,a,r)=toolAllowed(a)\land scopeAllows(u,a)\land tenant(u)=tenant(r).
\]

其中 \(u\) 是可信主体，\(a\) 是动作，\(r\) 是资源。这个简化条件只适用于教学数据；真实系统还可能需要对象所有者、部门、敏感级别、时间与用途条件。

把所有文件先检索给模型，再要求它“不要引用没有权限的”，已经把数据暴露了。权限过滤应在数据返回模型之前执行，且后续读取、下载与引用解析也要继续校验。

## 审批应该绑定到什么

用户批准删除 a2，不应使删除 a1 也通过；批准本次运行，也不应被下一次任务复用。本例审批令牌绑定：用户、租户、Run ID、工具名和资源 ID，同时设置过期时间。

```python
binding = hash_of([
    principal.user, principal.tenant,
    run_id, proposal.tool, proposal.resource_id
])
```

这是机制简写，实际代码用 JSON 编码后做 SHA-256，并将绑定保存到服务端随机令牌表。这里的哈希用于比较请求是否相同，不充当身份签名。令牌由可信服务端在真实确认之后签发，签发接口不注册成模型可调用的工具。

执行删除成功后消费令牌。若执行参数变化、跨 Run 复用或过期，都要重新走匹配规则。对于已经批准过的同一动作，应在授权范围内继续执行；不要让 Agent 每重试一次都无意义地询问同一问题。

## Agent 委派不能扩大权限

主 Agent 有 read 权限，子 Agent 不能因为名叫“AdminAgent”就获得 delete 权限。有效权限应受用户权限、应用权限和本次任务范围共同约束。授权上下文通过可信服务传递，模型只引用它的 ID；子任务应拿到完成工作所需的最小范围。

需要代理第三方服务时，除了 scope，还应检查凭据受众、过期和目标资源。Token 不能因为经过一个工具服务器就被当成通用通行证。具体协议按[Tools / MCP 域](../../05-tools-skills-protocols/README.md)当前版本学习，本篇只说明身份与权限原则。

## 正例和反例如何验证

[测试](../05-code/test_policy.py)不只检查拒绝：合法读取 a1 通过，批准后删除 a2 通过。随后验证同令牌删除不同对象、换用户、换 Run、过期、重复消费均被拒绝，并确认未授权对象没有消失。

本地实现把 Principal 看成已经认证的可信对象，没有实现登录或 OAuth；生产接口不能直接用客户端提交的 JSON 构造它。背景参考[NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)，示例审批机制与字段为本库设计。返回[本域导航](../README.md)。
