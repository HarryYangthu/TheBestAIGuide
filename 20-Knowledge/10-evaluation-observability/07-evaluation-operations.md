# 评测运营与发布门禁

> 状态：draft
> 目标：让评测从一次性跑分变成可维护的开发和生产反馈系统。

## 生命周期

```text
需求 / 真实失败
  -> Task 与成功条件
  -> Dev Suite 快速迭代
  -> Validation 比较方案
  -> Regression + Safety Gate
  -> Shadow / A-B / 分阶段发布
  -> 生产监控与人工反馈
  -> 新失败回流到数据集
```

离线 Eval、线上监控、A/B 测试和用户研究互相补充，不能彼此替代。

## 套件分工

| 套件 | 触发频率 | 主要用途 |
| --- | --- | --- |
| Smoke | 每次本地改动 | 验证 Harness、工具和少量关键路径可运行 |
| Regression | PR 或每日 | 防止已知能力退化 |
| Capability | 定期或模型升级 | 观察能力上限与新功能 |
| Safety | PR、发布前、定期对抗测试 | 权限、注入、泄露和高影响行为 |
| Reliability | 发布前或定期 | 多 Trial、长程和故障恢复 |
| Shadow | 上线前后 | 在真实分布上观察但不执行真实副作用 |

## 版本与可比性

评测产物必须同时保存：

- 应用和 Harness 提交；
- 模型快照与推理参数；
- Prompt、Context Builder、工具和路由版本；
- Task、Fixture、Grader 和环境版本；
- 时间窗口、缓存和重试策略；
- 指标计算代码版本。

只要数据集、评分器或统计口径发生实质变化，就需要重新运行基线，并在趋势图上标注断点。

## 发布门禁

门禁分三层：

1. **必须通过**：核心功能、权限、数据完整性和关键安全任务。
2. **非劣比较**：总体质量和关键切片不能超出预先定义的回归容忍区间。
3. **权衡审查**：质量提升是否值得额外延迟和成本。

```yaml
release_decision:
  hard_gates:
    critical_tasks: "all_pass"
    permission_violations: 0
    data_leaks: 0
  comparisons:
    primary_quality: "non_inferior_to_baseline"
    critical_slices: "no_material_regression"
  tradeoffs:
    latency: "review"
    cost_per_success: "review"
  approver: "..."
```

示例没有提供通用数值阈值。阈值必须基于业务风险、样本量和历史波动制定。

## 失败处置

门禁失败后不要直接“调 Prompt 再跑一次”。先记录：

- 失败 Task 和 Trial；
- 第一次偏离预期的事件；
- 与基线的配对差异；
- 根因层和责任组件；
- 是产品回归、环境噪声还是 Grader 问题；
- 修复、豁免或回滚决策；
- 新增回归样本。

豁免必须有范围、原因、责任人和失效日期。

## 生产反馈

生产阶段关注：

- 输入分布和任务结构是否漂移；
- 工具错误、超时、人工接管和放弃率；
- 成本、延迟和重试的尾部；
- 用户反馈与离线分数是否背离；
- 新模型或上游服务版本变化；
- 线上事故能否被现有套件捕获。

生产数据进入评测集前要去敏、去重、确认授权并防止未来测试集泄露。

## 套件维护

- 定期删除没有区分度的重复任务，但保留关键历史锚点；
- 对接近满分的套件增加边界和组合任务；
- 评分器变化后重跑校准集；
- 抽查自动评测与人工判断分歧；
- 记录任务来源、覆盖范围和缺口；
- 将基础设施失败单独统计，不要静默丢弃；
- 对成本较高的套件采用分层运行，而非完全停止。

## 最小日报或 PR 报告

```text
被测版本与基线
任务/Trial 数、排除项和环境状态
硬门禁结果
主要指标及区间
关键切片与最大回归
成本和延迟变化
新增失败类型
发布、阻断或需人工审查的结论
```

报告应能让读者区分“代码和测试通过”“本地端到端可用”“线上分布验证”和“真实业务效果”。
