# 评分器与组合计分

> 状态：draft

## 三类评分器

| 类型 | 擅长 | 局限 |
| --- | --- | --- |
| Deterministic | 单元测试、Schema、数据库状态、权限、延迟和工具参数 | 难以判断开放式质量，规则可能过度严格 |
| Model-based | 语义正确性、覆盖度、风格、引用与开放式比较 | 非确定、会偏置和漂移，需要校准 |
| Human | 专家判断、用户体验、高影响与新型失败 | 慢、贵、存在标注者分歧 |

原则是用最便宜且有效的评分器验证每个维度，而不是默认让大模型判断所有内容。

## Deterministic Grader

优先验证 Outcome：

- 测试是否通过；
- 文件、数据库和 API 状态是否正确；
- 输出是否符合 Schema；
- 数值是否落在容差范围；
- 是否出现禁止动作；
- 资源和时间是否超过硬限制。

避免对开放文本做脆弱的精确字符串匹配。能接受多个等价结果时，将等价类和容差写入任务定义。

## Model-based Grader

一个可校准的 Rubric 应包含：

```yaml
dimension: "citation_grounding"
question: "回答中的关键事实是否被所给来源直接支持？"
inputs:
  - "task"
  - "answer"
  - "sources"
labels:
  pass: "所有关键事实都有直接支持"
  fail: "至少一个关键事实无支持或与来源冲突"
  insufficient: "材料不足，无法判断"
output_schema:
  label: "pass | fail | insufficient"
  evidence: ["source-id#location"]
  rationale: "简短理由"
```

实务要求：

- 一次只判断少量清晰维度；
- 强制输出证据位置和结构化标签；
- 提供 `insufficient`，避免被迫猜测；
- 固定模型快照、Prompt 和推理配置；
- 对顺序偏差做 A/B 位置交换；
- 用人工标注集测量一致性、漏判和误判；
- 模型或 Rubric 更新后重新校准。

## Human Grader

人工不是天然无误。需要：

- 明确的标注指南和正反例；
- 隐藏系统版本，减少品牌偏差；
- 多标注者重叠样本；
- 记录分歧和仲裁；
- 对高影响领域使用合适的领域专家；
- 定期复核标注一致性。

用户反馈、A/B 测试和专家审查回答的问题不同，不应混为一个“人工分”。

## 组合方式

### 硬门禁

安全、权限、数据完整性和核心功能通常适合二元门禁：任一关键项失败，整体不可发布。

### 分维度得分

对可权衡属性保留独立得分，例如正确性、覆盖度、可读性、延迟和成本。先看向量，再决定是否需要一个汇总分。

### 加权汇总

加权分适合排序或实验比较，但权重必须来自业务取舍，并与硬门禁分开：

```yaml
decision:
  required:
    functional_correctness: true
    permission_violation: false
  score:
    answer_quality: 0.5
    efficiency: 0.2
    user_preference: 0.3
```

权重和数值仅表示结构，不能作为通用阈值。

## 评分器也要评测

建立一个包含明确正例、反例、边界例和“不足以判断”样本的校准集，持续检查：

- 与专家标签的一致率；
- 假阳性和假阴性；
- 不同任务切片上的偏差；
- 多次调用的一致性；
- 模型、Prompt 或数据更新后的漂移；
- 是否容易被被测输出中的指令操纵。

评分器输入中的 Agent 输出属于不可信数据，不能覆盖 Rubric 或泄露参考答案。

## 常见误用

- 用流畅度代替事实正确性；
- 只看 Agent 自述，不检查最终状态；
- 将参考轨迹当作唯一合法路径；
- 一个 Judge 同时判断十几个模糊维度；
- 用同一模型生成答案、生成参考答案并打分，却不做人工校准；
- 评分器版本变化后继续与历史分数直接比较。
