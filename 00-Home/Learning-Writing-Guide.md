# 面向学习的写作要求

本库服务读者的系统学习和实践。读完一个主题，读者应能说清它实际做了什么、为什么这样做、何时适用，并从文章找到可以运行的实现。

## 先把机制讲透

直接从一个有用的问题进入主题。每个段落回答一个具体问题，解释原因和结果。少用抽象口号，避免反复说“至关重要”“构建闭环”“提升赋能”。术语首次出现时解释含义，后续使用同一称呼。

例如 Attention 中的 QK 转置乘积，要讲清楚每个点积对应哪个查询位置与哪个候选位置、为何它是学习到的匹配分数；不要只把公式读一遍。再解释缩放、Softmax、掩码和对 Value 加权的计算，指出点积分数不是统计学相关系数，也不自动是可解释的因果重要性。

## 让读者跟得上每一步

默认读者会基础 Python，但未必做过 Agent 系统。不要用一个尚未解释的术语解释另一个术语。先把具体事情说出来，再给它名称，例如：“程序记录当前做到哪一步，这份记录叫 State。”随后展示记录中实际有哪些值，以及下一次操作会改哪个值。

下面两段谈的是同一件事，后一段才把发生过程交给了读者。

> 太抽象：通过乐观锁保证并发更新一致性，并对冲突执行受控处理。

> 展开后：两个子任务都读到了版本 3。第一个把结果保存成版本 4；第二个手里仍然是版本 3，如果直接写回，就可能覆盖刚保存的结果。所以第二个保存时要同时说“我是在版本 3 上修改的”。程序发现当前已经是版本 4，先拒绝这次写入，让它重新读取后再合并。这种做法通常叫乐观并发控制。

“职责、输入输出、失败模式、验收要求”可以帮助作者检查有没有遗漏，但不必每篇都照着这些栏目排版。正文应围绕具体问题展开：为什么需要它，第一次尝试为什么失败，改了哪一步，中间数据怎样变化，结果为什么不同。表格适合并排比较，不要用连续的大表格替代解释。

一个知识点讲完后，读者应能拿笔演算一次，或对照短代码逐步说出变量的变化。只有字段名、公式或一段调用命令，仍然不算讲完。英文名首次出现时给出中文含义；能用“读文件、保存、等待、比较”说清的地方，不要换成“消费产物、落实门禁、构建闭环”。

## 公式、例子与代码相连

公式说明它计算的对象，定义符号、矩阵形状和适用假设。关键公式至少配一个数值例子或可执行验证。说明每一步怎样得到下一步，避免用“显然”“不难证明”跳过理解所需的推导。

面向 GitHub 阅读时，行内公式使用 `$...$`，独立公式使用 `$$...$$`，代码围栏只放代码或明确标注的伪代码。写法依据 [GitHub 数学表达式文档](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)；表格中避免未转义的竖线拆开公式列。公式应当能在阅读页直接辨认，而不是只留下 LaTeX 源码。

Markdown 保留帮助理解的核心代码；新组件的完整实现进入 `code/`，Notebook 按阅读顺序放在同一组件目录；归档保留原来的 `05-code/` 与 `04-labs/`。三者使用相对链接连接，源码不要求读者从多个代码块自行拼装。代码中注明输入、输出、关键张量维度和异常行为，注释解释设计原因。

Notebook 使用小而具体的输入，按顺序运行、展示中间量、对比基线和变化，最后解释结果及局限。人工构造的数据注明“教学数据”，不伪装成真实业务样本。参考实现、真实模型运行和生产效果分别陈述。

读源码时先展示最关键的几行，并说明这段代码之前已经准备了什么。代码之后解释关键变量和分支为什么存在。删去日志、异常处理或辅助函数时，明确说明这是节选或简化示例，不让读者误以为可以直接复制成完整工程。运行命令必须说明工作目录、必要环境和输出位置，并告诉读者应观察哪个字段；练习要附参考解释，使独立学习者能够核对自己的理解。

## 内容深度与结构

新组件以一个小任务贯穿全章，从最小操作逐步增加必要机制。README 负责阅读顺序与公共环境，每份实质章节开头给出总览图，下面的子节逐步实现图中的节点；目录中的编号表示阅读顺序。

标题使用简短、具体的概念或对象名，如“API 配置”“工具定义”“参数解析”“消息历史”，原因与作用放在正文。图前直接写“本章总览图如下：”，不再复述整张图或预告后文写作过程。

术语应指向实际代码。模型配置直接说明填写 URL、API Key 和模型名；`client` 是 `OpenAI(...)` 创建的 SDK 对象，用于发送请求。“配置客户端”不能代替这些具体操作。

文件中提到的笔记、数据与待修复代码必须随章提供。每段代码明确是独立程序、接续片段、函数、格式示例还是源码节选，并交代工作目录、命令、标准输出或返回值、产物位置。确定性输出应能逐行核对；模型回答、耗时和动态编号只给参考输出或字段结构。

涉及模型的主线默认使用真实 OpenAI SDK，提供 `OPENAI_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL` 三项配置与 `.env.example`；缺配置时明确报错。固定响应只放在显式测试入口。用“本文响应字典”等具体名称解释协议转换，展示 JSON 字符串、Python 字典与关联 ID 的关系。

实验沿同一任务改变一个条件，报告读取实际记录生成；未执行的 API 单元保持未执行状态。验证范围集中说明一次，减少正文中重复的边界提醒。完成后沿 README 实际走读，检查输入、命令、图、代码与产物能否相互对应。

概念篇讲定义、机制、例子、边界、常见错误和必要来源。模式篇讲解决什么问题、如何实施、依赖条件、代价和验证。案例篇给输入、过程、选择依据、结果证据和失败。按主题需要安排章节，不强制所有文章套同一套空模板。

文章用连贯段落讲因果，表格比较方案或映射关系，列表说明步骤。保持信息密度；既不堆术语，也不把同一句话用多种表达重复。主线先讲最需要掌握的内容，进阶方法通过独立小节或链接扩展。

## 完成检查

1. 能否用自己的话解释核心机制，而不只是背定义？
2. 关键公式的符号、形状、假设和计算步骤是否明确？
3. 是否能从具体失败选择合适的解决方法，并知道代价？
4. 是否有真实可运行的对应代码或明确标为推导/伪代码的示例？
5. 文章、实现、实验和来源能否互相找到？
6. 每个实验结论是否有实际输出支撑，未运行路径是否如实标注？

这些检查用于提高学习效果，不用字数、文件数或术语数量代替质量。
